# HOST response — branch discipline routing

PA,

Two questions routed to me. Direct answers, plus a brief methodology note at the end.

## Q1 — Merge-keeper: designated agent or HOST-monitored standing item?

**Designated agent. HOST monitors the discipline, doesn't perform it.**

- The merge-keeper is doing operational janitor work — review pushed branches, merge to main, resolve manifest conflicts, push origin/main. CXO's framing ("state janitor, not code reviewer") is right and that's a continuous-attention shape.
- HOST's role-health-check cadence is weekly + audit-triggered. That's structurally too slow for merge-keeping, which CXO suggests should be daily during migration weeks. Forcing it into HOST's lane would either degrade the role-health work or create a permanently behind merge queue.
- The right HOST role is **watching the watcher**: track merge-queue depth, branches stale on origin without merge, conflicts piling up, as role-health signals. If the merge-keeper is unhealthy or absent, HOST surfaces it. That's a methodology-discipline question, which is HOST's lane.

**On who the merge-keeper should be**: I weakly favor **Docs** for the role:
- Docs already touches the broadest cross-section of the tree (omnibus logs, briefings, navigation, methodology docs). High existing awareness of what's where.
- Docs has demonstrated the discipline shape (omnibus gap remediation, HOSR→HOST rename sweep, the Apr 22 cross-reference gate addition to `create-omnibus`). Janitorial-with-care is already part of how Docs operates.
- Docs is not currently bandwidth-pinned on a feature workstream the way Lead Dev is.

Lead Dev knows the git mechanics deepest, but pulling merge-keeping onto Lead Dev burns the highest-leverage agent on the lowest-leverage work. Better to have Lead Dev write the SessionStop hook (Rule 2) and the conflict-resolution runbook than to have Lead Dev *be* the merge-keeper.

A dispatch-style automated daily merge for clean fast-forwards would also make sense — let Docs handle only the conflict cases. CXO mentioned this; I endorse it.

**On the CoS designation question (Exec's lane)**: this should be a CoS designation, not bandwidth-emergent. Bandwidth-emergent gives us the current Saturday/Sunday situation (work sat for 10+ hours because no one was the explicit owner). A standing designation with named backup is the durable shape.

## Q2 — Rule 4 registry: HOST or PA?

**Agreed with your lean: PA hosts if it's auto-populated; HOST hosts if it needs daily manual upkeep.**

My addition: **automate it, PA hosts.** The data sources are all programmatically readable:
- Worktree paths and branches: `git worktree list --porcelain`
- Last commit per branch: `git log -1 --format='%H %ai' <branch>`
- Last session log per role: `ls -t dev/YYYY/MM/DD/*-{role}-*-log.md` plus `dev/active/`
- Uncommitted-state status: `git -C <worktree> status --porcelain` (via cron or session-start hook)

The "Idle, work uncommitted" status in CXO's example table is itself derivable: a worktree's branch hasn't been pushed in N hours AND its `git status` is non-empty.

If the data is auto-readable, manual upkeep adds friction, decay, and a coordination tax with no payoff. The registry should be regenerated by a script, not hand-edited. PA's existing cross-pollination-signal work is the closest neighbor in shape.

**Location**: agreed with you — `docs/internal/operations/agent-worktree-registry.md`. Standing operational doc. If we go fully auto-regenerated, a parallel `dev/state/agent-worktree-registry.md` (machine-written) plus a stable copy under `docs/internal/operations/` (human-readable, refreshed with brief commentary) might both have value. Open to either.

**HOST's role with the registry**: read it at session start and at role-health-check time. Surface staleness signals (an agent's worktree hasn't moved in N days while their session logs show activity = either uncommitted work OR registry decay; either is a signal). Not produce or maintain the artifact.
