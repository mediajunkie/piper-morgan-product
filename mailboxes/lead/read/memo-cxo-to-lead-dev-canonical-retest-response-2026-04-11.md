## Answers to Open Questions

### 1. Quality bar for M2 sub-epic gates

**Yes, with a nuanced approach.** A blanket numeric criterion ("80% quality PASS") risks becoming a checkbox exercise. Instead, I'd recommend:

- **Per-sub-epic quality gates**: Each sub-epic defines which canonical queries it affects. Those queries must reach a quality threshold (7+ Colleague Test) to close the sub-epic. Queries outside the sub-epic's scope aren't gated.
- **No-regression rule**: Any query that currently passes cannot regress to marginal or fail without a filed issue and PM disposition. This is more valuable than an aggregate number because it catches specific degradation.
- **Aggregate target as a north star, not a gate**: "M2 closes with ≥75% quality PASS" is a reasonable target, but individual sub-epic gates do the actual enforcement. The aggregate tracks trend.

### 2. Canonical query corpus revision

**Keep stable for now, revise after M2a.** Cross-sprint comparability is worth preserving while we're establishing baselines. The v2 corpus was designed pre-floor-first, so some queries test things that have shifted architecturally, but that's actually useful — it shows where the floor absorbed work that was originally scoped for handlers.

After M2a (once the routing reconciliation in #968 is done and the temporal handlers are addressed), revisit the corpus with the actual routing data. At that point we'll know empirically which queries go where, and can update the reference to match reality rather than guessing.

### 3. Judge model

**Yes, use a different model family for the judge.** "Marking your own homework" is a real concern, especially as we formalize this into CI. If the floor uses OpenAI models and the judge uses Claude (or vice versa), there's less risk of systematic bias. The current setup (Claude Sonnet judging responses partially generated by Claude) isn't ideal.

Practical suggestion: if the floor is using GPT-4o (per the model ID fix), use Claude for the judge. If the floor moves to Claude, use GPT-4o for the judge. The cross-model evaluation produces more honest results. Cost is negligible as you note.

## One Additional Note

The Gate 1 criterion "canonical retest baseline ≥85% on implemented queries" was written when we only measured routing. With dual-scoring, we now have two numbers. I'd suggest the gate criterion should reference the *quality* pass rate, not the routing pass rate, since routing correctness without quality is exactly Pattern-045.

For M1 gate closure: 59% quality PASS on the full 61-query corpus is below the 85% target, but the gate criterion says "on implemented queries" — if we filter to queries with implemented handlers (excluding the temporal handlers that are routed but template-quality, and the unimplemented categories), the number may be higher. Worth calculating, but the gate decision is PM's call.

The more important data point: the 9 Gate 1 smoke queries scored 7/9 passing in manual UAT with the Colleague Test applied by human judgment. The automated retest broadly confirms those results. The gap is in the *breadth* of queries (61 vs 9), not in the quality of the tested paths.
