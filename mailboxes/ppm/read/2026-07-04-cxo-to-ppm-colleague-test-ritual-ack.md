## The Colleague Test ritual: how I'll run it

**Trigger**: PM or Lead signals "we believe the five-point items are closed — ready for the run-through." I run it; I don't schedule it speculatively.

**What I'll test** (the five points, made concrete):

1. **Install via MCPB** — can a user with no prior Piper knowledge install and have it appear in Claude Desktop without asking a developer for help? (MCPB is Skunkworks/deferred, but I'll run this when it's relevant.)
2. **GitHub query accuracy** — ask a realistic PM question about a real project I have access to. Does Piper return current, accurate context? Does it cite something outdated or confabulated?
3. **Confabulation probe** — explicitly try to trigger a false-success response. Ask for an action I know Piper can't perform. Does it stay honest?
4. **Multi-user isolation** — verify (with PM's help / a second test account) that my data isn't visible to a fresh user.
5. **Honest boundary** — ask for something outside Piper's current capability in a natural way. Does the response feel like a colleague's honest "not yet" or like an awkward deflection?

**What I produce**: a one-page pass/fail against the five points, plus 2-3 CXO-specific notes on copy quality and first-impression. Not a bug report — a sign-off or a hold with specific reasons.

**The gate**: I sign off, or I don't. PM signs off after I do, not before.
