# Generated docs: YES — they exist, persist, and /files already surfaces them (#355)

PPM's gating question — *"does Piper produce durable documents today?"* — **Yes, with evidence.** And the investigation surfaced a bigger finding: **the "one surface, source is a facet" model you + CXO are converging on is already ~80% built** as #355. #1270 is consolidate + honest-badge + rename, **not** a from-scratch object model.

## Evidence: generated content persists durably today
- **Save path**: `POST /api/v1/artifacts` (`web/api/routes/artifacts.py:71`, `save_artifact`) — docstring: *"Persist a chat output as a generated Artifact (owner = current user)"* → creates `Artifact(source_type=ArtifactSourceType.GENERATED, lifecycle_state=RATIFIED, owner_id=current_user.sub)` and writes it to the durable **`artifacts` table** (`ArtifactDB`, `services/database/models.py:1158`). Owner-anchored (ADR-071 D2-clean), RATIFIED = a deliberate user keep.
- **UI affordance exists**: `web/static/js/chat.js:295` — a save-from-chat action POSTs the reply as a GENERATED artifact. So users produce these today.
- **Router is live**: `web/app.py:239` mounts the Artifacts API (not dead code).

→ **Generated source type IS Beta-scopable.** The persistence + production mechanism already exists; what's left is surfacing/naming/honest-badging — the same shape as uploaded, not new backend. So your "Beta-conditional" row resolves to **YES** for generated.

## The bigger finding: the unified-source view already exists (#355)
`/files` is **already a view over two sources**: `web/api/routes/files.py:278` — *"also surface saved generated Artifacts in the browser. **Artifact is the system-of-record; /files is a view.**"* Generated artifacts appear alongside uploaded files as `kind:"artifact"`, and `templates/files.html` already:
- **routes actions by source** — artifact→`/api/v1/artifacts`, file→`/api/v1/files` (rename #1184, delete, download, preview, tags) (files.html:379+)
- offers a **source filter** — `<option value="artifact">Generated artifacts</option>` (files.html:287)

So CXO's "one Documents surface, source is a facet/filter" is **substantially the #355 design already shipped.** This materially shrinks #1270.

## One reconcile for your enum addendum (PPM)
There are already **two** source taxonomies in the code:
- `ArtifactSourceType` (`services/domain/models.py:843`): `DOCUMENT | UPLOADED_FILE | INSIGHT | GENERATED` — the #952 Artifact unifying lens (Arch-ratified 2026-06-08), and the one `/files` actually keys off.
- `DocumentDB.source` — a free-text provenance string on uploaded-doc rows.

Your proposed `ProvenanceSource` addendum (`PIPER_GENERATED`, `FEDERATED`) should **reconcile with / map onto `ArtifactSourceType.GENERATED`** (same concept), not stand up a third parallel taxonomy. The cleanest object model may already be in the tree: **`Artifact` IS the parent entity** — it already unifies DOCUMENT/UPLOADED_FILE/INSIGHT/GENERATED; `source` is its `source_type` facet; federated becomes a 5th `ArtifactSourceType` value when RECONNECT lands. Worth a line in your addendum on **which enum is canonical** so I build against one, not two.
