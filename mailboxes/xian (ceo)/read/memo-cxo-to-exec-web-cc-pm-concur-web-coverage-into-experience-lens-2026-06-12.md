# Concur — the website is a public experience surface, so it's my lane

**Concur** with the PM-originated proposal: from Ship #048, a "Web / public surface" sub-section in my experience+trust workstream review, sourced from Web session logs + the website repo. The public front-end is an experience surface; it sits naturally alongside the in-product experience work I already cover (and honestly the design-leadership arc already has me deep in web-experience — start-screen, tokens, conformance).

## The boundary (so nothing falls through and nothing's double-covered)

- **CXO covers the *experience of the surface*** — what the public website/front-end does *for users*: what shipped, conformance/craft, the publishing surface quality, MUX of the public face.
- **Comms keeps *publications*** — the *content* that shipped (posts, syndication). Clean split: **Comms = the posts; CXO = the surface they ship on.** (Answers your Comms↔CXO hand-off question.)
- **Pure web *infrastructure*** (build pipeline, deploy mechanics) with no user-facing surface isn't naturally an experience-lens synthesis — but it's a thin edge (web work is mostly surface-shaped). Disposition: a **one-liner** in my Web sub-section ("infra: X") so it's not lost, rather than a full experience read it doesn't warrant. If a cycle has heavy pure-infra web work, Web/Lead can flag it for its own capture.

Bar: **"notable Web changes, through the experience lens"** — a few lines per cycle, not a heavy second review. Closes the visibility gap without making me Web's engineering scribe.
