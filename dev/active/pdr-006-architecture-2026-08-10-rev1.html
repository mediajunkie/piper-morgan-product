Hosted MCP endpoint & plugin distribution

Piper's server holds tools, connectors and persisted context. The client's model does the reasoning — and composes what the user actually reads.

Scope of this page This is one surface's architecture — chat hosts reached through the plugin + hosted MCP endpoint — not the architecture of Piper. Web, Slack, phone and CLI have their own jobs and are not drawn here because they don't route through this endpoint, not because they've gone away. Why that distinction is the point of this revision ↓

Caller-identity boundary — fail closed Every call resolves to an owner_id before touching server state. No identity, no read. Never default to a system or anonymous owner. All ADR-079 owner-scoping sits downstream of this line — a handler reached with a caller-chosen identity produces a read that looks correctly scoped while the owner is the forged thing, and the derived lint cannot see it. carrier confirmed a plugin's headersHelper supplies dynamic per-request auth headers — the boundary has a named transport now, not just a requirement.

The consequence worth sitting with — narrowed to where it actually applies

Our first alpha tester's verdict was "just an LLM with extra UI." On the chat-host surface specifically, that becomes true by design — it is their model, plus our tools, because we don't control that surface's rendering. This does not generalise to Piper as a whole: web has radar and a UI we do control; that's the surface where "extra UI" isn't the complaint, because there the interface is ours to make good.

We have never tested whether our honesty survives recomposition by a model we don't control. That risk is real and unchanged since July — see the gate below, which now has actual evidence rather than just the concern.

Ratified ≠ shippable

#1458 — cross-caller state isolation open

Redis, in-process floor/context state, and rate-limiting were never traced. The question moved from "can an anonymous caller see state" to "can caller A see caller B's" — strictly harder. Blocks multi-tenant serving. Unchanged since July; no new evidence either direction.

#1463 — verification rubric branch open, with new evidence

No existing rubric fits a surface where the client's model writes the user-visible reply. Probe A ran since July: refusals survive as failure-shaped payloads, 6/6 across both Claude and GPT — structured fields help but are not sufficient on GPT. API-layer only; a deployed-host retest is still pending, and it's blocked on the endpoint above not existing yet, not on anything ops-side.

Corrected since July: mcp.pipermorgan.ai is still not deployed (the server package is unbuilt, not merely undeployed). The privacy-policy line was wrong outright — a page exists at pipermorgan.ai/privacy and returns 200. What's actually open: whether its content is substantive (server-rendered text is 29 characters; can't confirm from an agent seat whether a browser renders more) and three unresolved items — sub-processor completeness, retention practice, contact address. A directory listing still needs domain-ownership verification either way.

One distinction that keeps getting collapsed

services/mcp/consumer/ is Piper as an MCP client, calling out to other people's servers. mcp.pipermorgan.ai is Piper as an MCP server, being called in. Opposite directions.

A live consumer family — CORE-MCP-MIGRATION #198 — precedents nothing about the server side, which is where the identity risk above actually lives.

Where BYOC sits in the sequence

PM's ruling, 2026-08-26: BYOC is one track that forks into two destinations once the shared foundation is done — not a parallel, beta-primary effort competing with it. This page's own gap note above (services/mcp/server/ doesn't exist yet) is what makes that concrete: hosted-MCP delivery is sequenced after the shared grammar work, not literally alongside it. Connector shims vs. real MCP — a distinction the "Connectors" chip above was hiding

GitHub, Slack, and Notion each now ship an official, vendor-hosted remote MCP server — api.githubcopilot.com/mcp/, mcp.slack.com/mcp (GA 2026-02-17), mcp.notion.com/mcp. Checked directly against Piper's own services/mcp/consumer/ adapters rather than assumed from the chip label above:

ConnectorWhat's actually underneath
GitHubMostly the real thing — 8 live call_tool() sites over a real MCP transport. Talks to a self-hosted instance of the OSS github-mcp-server, not GitHub's now-official hosted endpoint — a config-level simplification candidate (ADR-070's own server-ref resolver already supports repointing it), flagged to Lead/Arch, not decided here.
Slack, NotionZero real MCP tool calls in either adapter (grep-verified). Both are connector-contract shims (#1232/ADR-070 D5 connect/status/resolve/degrade) wrapping fully bespoke REST code underneath. The shim's presence can read as "this connector is on the current architecture" when only the outer contract is.
