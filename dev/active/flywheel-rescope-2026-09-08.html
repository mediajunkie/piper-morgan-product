The flywheel's practice layer expired four months ago, and it says so itself

A scope for re-deriving Methodology-00 Layer 2 against the tooling stack we actually run on. Not a proposal to change what the flywheel means — a proposal to update what it asks people to do.

Exec · 8 September 2026 · requested by PM after finding that the duty cycle has no intake from the product backlog

Why now

PM: "Something has been lost despite this huge autonomy improvement and I honestly don't understand it… I feel like the excellence flywheel is due for a re-evaluation against our current tooling stack."

The triggering symptom, found this morning: the duty-cycle-tick procedure defines available work as an agent's inbox plus their own standing-items file. No step reads the sprint board, the milestone, or open issues. So "there is no work" and "28 items are open" are simultaneously true, and a role reporting the first while the second holds is following the procedure correctly.

That is one symptom. The scope below is about the mechanism that produced it — a practice layer written for a world where PM assigned work, still in force in a world where eleven agents wake on timers and assign their own.

methodology-00-EXCELLENCE-FLYWHEEL.md, v2.0, dated 26 April 2026, is explicit about its own structure:

That is the same shape as every other finding this month: the mechanism was written down, and writing it down was not a chokepoint.

The questions the re-evaluation should answer

Q1 — the triggering one

Where does work come from?

The five practices tell you how to do work well. None of them tells you how to find it. That was fine when PM assigned it. Under agent-pull it is the load-bearing gap, and today's near-term fix (pull from the Sprint Backlog when otherwise idle) is a patch on it, not an answer to it.

Arch + PPM

Q2 — the one I'd expect to be contentious

Five practices, or fifty-three methodology entries?

Layer 2 names five practices. The methodology corpus now holds 53 entries, several filed this week, and they are what agents actually cite day to day — m-43, m-44, m-49, m-50, m-51. Is the practice layer still canonical, or has it been quietly superseded by a corpus nobody reconciled it against? If the latter, saying so is more valuable than adding a sixth practice.

CIO + Docs

Q3

Which of the five still hold under autonomy, unchanged?

Not a rewrite by default. Verify Before Building and Track to Completion with Evidence look durable. Coordinate Through Structure was written for a smaller cohort with different surfaces. The answer "four of five stand" is a good outcome and should be reachable.

Arch

Q4

What practices does the autonomous era need that didn't exist in April?

Candidates the cohort has already paid for and never promoted: chokepoint-vs-bolt-on (a duty survives only if skipping it visibly breaks work already in progress), a self-report is not evidence, state the denominator, name the layer you measured. These are live and load-bearing and none is in Layer 2.

CIO + HOST

Q5

Is idle a legitimate terminal state?

Today's directive says no for Lead. Is that role-specific or general? A governance role with an empty inbox arguably should idle; a build role with 28 open items should not. The flywheel currently has no vocabulary for that distinction, which is why it never surfaced as a question.

PM + Arch

What done looks like

A revised Layer 2 — practices re-derived for agent-pull work intake, each one traceable to operational evidence from the autonomous period rather than carried forward on authority.

An explicit reconciliation with the 53-entry corpus — either the practice layer is the index and the corpus is its detail, or the practice layer is historical and the corpus is canonical. Ambiguity here is the actual defect; either answer beats it.

A stated review trigger. v2.0 said the practice layer evolves with the project and nothing made that happen. Whatever v3 says, it needs a condition that fires — a milestone close, a stack change — not an intention.

Explicitly out of scope

  • Layer 1. "Quality compounds into velocity" is right and the July 2025 formulation got it right. Not reopening it.
  • Per-role mnemonics. Divergence there is explicitly fine per v2.0. Touch only where Layer 2 forces it.
  • The near-term backlog fix. Already directed to Lead today. This scope must not become the reason that waits.
  • Rewriting duty-cycle-tick. The intake step is a separate, faster change already routed to CIO. If this scope absorbs it, the fix ships in weeks instead of days.

The risk worth naming out loud

This cohort has spent a month establishing that new obligations decay unless they ride on something that already can't be skipped. A methodology re-evaluation is exactly the kind of work that produces a beautiful document nobody's daily loop touches.

The test I'd hold it to: if the output is a revised Layer 2 that no procedure reads, we have written a better description of a flywheel while the flywheel keeps missing its intake. Every practice in v3 should name where in a live procedure it is enforced — or be marked explicitly as aspirational.

Recommended shape: Arch leads, CIO and Docs on Q2, HOST on Q4, PM rules Q5. One synthesis, reviewed before adoption the way ESSENCE was. Not a duty-cycle item — a scoped piece of work with a start and an end, because a standing obligation to re-evaluate the flywheel is precisely the bolt-on this document warns about.
