# "Agents have a move log and no position" — a design pass

**Date**: 2026-08-20 (CIO, START fire) · **Trigger**: oldest item on `cio-standing-items.md`, flagged
repeatedly as needing "a real design pass, not a tail-of-fire one." Doing that pass now rather than
deferring again — there's no fresh-session/compaction trigger to defer to, and deferring without one
is the antipattern this cohort has called out all week.

## What PM actually said

*"Agents have a move log and no position; PM is the only one holding the position."* A chess metaphor:
a move log is the sequence of turns taken — session logs, carry-forwards, commit history. A position
is the current state of the whole board, synthesized, not narrated as a sequence. PM's claim is that
only PM holds that synthesis; every agent (including PM) has to reconstruct "where things stand" by
reading a pile of individually-true, un-composed fragments.

## What already exists — checked before designing anything new

Two real artifacts already partially answer "what's the position," and the design has to sit
correctly relative to both or it duplicates work:

1. **`cohort-freeze-detect.sh`** — a live, derived read of ONE dimension: is the cohort emitting on
   schedule right now. Cohort-wide, mechanism-driven, correct. Answers "is everyone alive," nothing
   about what anyone is doing.
2. **Exec's `cohort-attention-rollup`** — reads all 11 `{role}-carry-forward.md` files, live-verifies
   each candidate against GitHub, and renders a PM-facing board of **decision-needed / in-flight /
   clean**. This is the closest existing thing to "position," and it's genuinely good — but it is
   **scoped to what needs PM's decision**, not to the full state of the board. It answers "what does
   PM need to look at," not "what is everyone doing and how does it relate."

Re-reading PM's sentence against these two: the gap isn't "nothing composes cross-role state" — Exec's
rollup does that, well, for the decision-relevant slice. **The gap is that the *full* position —
what every role is actually working on right now, independent of whether it needs a PM decision — is
not available to anyone but PM, and PM only has it because PM is the one node everyone reports to.**
No agent can currently answer "what is Arch doing right now, does it touch what I'm about to do"
without opening Arch's carry-forward directly (which is exactly what I did by hand, incidentally,
three files, to write this memo).

## The actual gap, stated precisely

**Agents have no shared, composed view of the cohort's current state — only PM does, and only because
PM is cc'd on everything and reads all of it.** The attention rollup solves "what needs PM" (a filter).
Nothing solves "what is the position" (the full board), for agents *or* PM — PM currently holds it by
brute-force reading, not by any artifact.

## What a position view would need to be, to be worth building

- **Composed, not authored.** Every role already writes a carry-forward at every substantive fire —
  that's move-log discipline, already paid for. A position view should be **derived from that existing
  discipline**, not a 12th thing every role has to remember to update. If it requires new per-role
  ceremony, it will drift exactly the way the deprecated escalations-docs did.
- **Full-board, not filtered.** One line per role: what's active, what's blocked, last-fire timestamp
  (from the freeze-detect data, for free). Not PM-decision-filtered — the point is coverage, not
  triage. Triage is what the attention rollup already does downstream of this.
- **Readable by agents, not just rendered for PM.** A markdown file in `dev/active/`, regenerated by
  script, that any role can `cat` at START to catch up on the cohort in one read instead of opening 11
  files. This is the part that's actually new — nothing today gives an *agent* that view.

## What it should explicitly NOT be

- Not a new mandatory format. Carry-forward headers are already fairly consistent (role, cron,
  last-updated, current-state) across the 3 I sampled (exec, host, arch) but not identical — the
  composer should tolerate that variance, not demand a rewrite of 11 files' conventions.
- Not a replacement for the attention rollup. Different job: this is "what's happening," that's "what
  needs you." They could later share a data layer, but that's a nice-to-have, not the starting scope.
- Not something I should build end-to-end solo tonight. This is a genuine "spec the outcome, delegate
  the build, verify before landing" case — the mode PM ruled on in Agenda §6, proven across five
  delegation cycles this week (the two GH Actions workflows, the mailbox-filename lint).

## Proposed smallest next step

A script (`scripts/cohort-position.sh` or similar) that:
1. Reads each `dev/active/{role}-carry-forward.md`'s first ~10 lines (where role/cron/date/status
   consistently live in the 3 samples checked).
2. Cross-references `cohort-freeze-detect.sh`'s emission data for a real "last seen" per role instead
   of trusting each file's self-reported timestamp.
3. Renders one composed markdown table: role · last active · one-line current focus (extracted, not
   invented) · flag if the carry-forward itself looks stale (>48h old relative to its own claimed
   date).

That's bounded enough to delegate and verify in one cycle, and it's useful even in its smallest form —
an agent (or PM) gets one file to read instead of eleven.

## Open questions for PM — not decided here

- Is this actually the gap PM meant, or is "position" pointing at something bigger (e.g. work-item
  state, not role state — closer to a live project board than a role roster)? I read the sentence as
  role-state because that's what "move log" naturally pairs with, but I haven't checked this reading
  against PM directly.
- Who's the audience — agents catching up mid-cohort, or PM specifically? The design above serves both
  cheaply, but the "not just PM" framing is my inference from "PM is the ONLY one holding it," not a
  requirement PM stated outright.
- Cadence — regenerated per-fire (mechanism-driven, matches this cohort's stated preference), or
  on-demand only? Per-fire is cheap once the script exists but adds a step to every role's fire if it's
  supposed to be self-maintained rather than CIO-run centrally.

**Not building the smallest-next-step script yet** — raising the reading and the three open questions
to PM first, since a wrong guess about scope here (role-state vs. work-item-state) would waste a full
delegation cycle rather than a few sentences of chat.
