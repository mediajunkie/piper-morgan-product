Memory-index format — the choice, and where it's written down

Full doc: docs/internal/operations/memory-index-size-limits.md. Live state: 193 lines against a ~200-line ceiling, 174 memories. Past the ceiling, trailing entries vanish from every agent's context silently — and both the byte and line limits were tested against the platform's claimed fix, which does not hold.

The choice is between three levers, and the deciding property is reversibility. ① Denser entry format — drop or shorten the one-line descriptions. Generator change, re-runnable, costs recall quality since the description is what makes an index useful. ② Per-type index files with a router — proposed, tested, and withdrawn by its own author: only MEMORY.md is auto-loaded (174 files sit unloaded), so a split moves entries off the loaded surface rather than raising the ceiling. ③ Prune entries — the only irreversible option, since memory isn't version-controlled, and a governance call about other roles' lessons rather than a formatting choice.

My recommendation: ①, and treat it as buying time rather than solving it. One line per memory means the floor rises with every new memory regardless of format — the structural question is whether the cohort keeps growing a shared pool indefinitely, and that one is genuinely yours.
