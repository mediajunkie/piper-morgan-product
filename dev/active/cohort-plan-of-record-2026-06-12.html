Canonical (Option B / "Model B"): every duty-cycle session launches from Claude Desktop with the worktree checkbox ON. Desktop auto-creates an ephemeral worktree (random branch name — this is fine and normal). The agent does all substantive work there and pushes finished units to origin/main. The main checkout is touched only for mailbox operations, via the bridge pattern: git -C /path/to/main-checkout add/commit/push.
Deprecated (Model A — dedicated named worktrees): the long-lived claude/{role}-cycle sibling checkouts. Why deprecated: (1) they clutter PM's searches with multiple indexed repo copies; (2) two patterns running side-by-side caused real confusion (Exec's 6/12 migration); (3) branch persistence isn't load-bearing — every artifact pushes to main anyway; the carry-forward file (on main) is the continuity mechanism, not the branch. Cleanup: existing dedicated worktrees get removed as each role migrates (git worktree remove ../piper-morgan-product-{role}-cycle).
Exception rubric (PM-approved case-by-case): a role may keep a named long-lived worktree only for multi-day in-branch WIP that genuinely doesn't push to main between sessions, with explicit PM approval. RESOLVED 2026-06-12 — there are NO current exceptions. Lead Dev (the only candidate; dev server on :8001 binds to a worktree path) determined empirically that the ephemeral worktree suffices: it nests inside the main checkout, so the server's find_dotenv() walks up and finds main's .env/venv (the predecessor's sibling worktree couldn't — that copy-burden is what made a named worktree feel necessary), and a session-start restart is needed anyway for code freshness (mooting process-persistence, the only real advantage). The nested-walk-up property generalizes to any ephemeral worktree → no role needs an exception on server-binding grounds. (LD session log 2026-06-12 §4; PROVEN by an actual restart: PID 37522, /health 200, Slack connected, 0 API errors.)

2 · The Mailbox Discipline (unchanged, now the only main-touch)

  • Mail moves on main, immediately, per memo — write memo → cc copies → sent mirror → triage moves → git add (explicit paths, BOTH sides of any inbox→read move) → commit → push.
  • check-branch.sh hard-blocks mailbox commits on any non-main branch — the bridge isn't optional.
  • New since 6/12 (#1106): after mail moves, the recipient regenerates their own MANIFESTs — python scripts/regenerate-mailbox-manifests.py --role {role}. Single-writer, idempotent. Curated prose goes below the <!-- curated --> marker, where regens preserve it verbatim.

The per-role migration runbook (what PM does each time)

1. Paste the role's HANDOFF prompt into the OLD session
   → agent captures carry-forward, clears cron, pushes everything, reports back
2. Verify the report (crons clear; `git log main..HEAD` empty)
3. Close the old session
4. Launch new session: Desktop → Local → piper-morgan-product → main
   → worktree ☑ → model per the role-model map
   → .env EMPTY (never ANTHROPIC_API_KEY=; optionally GIT_AUTHOR_NAME=mediajunkie)
5. Paste the role's BOOTSTRAP brief as the first message
6. Wait for the report-back; spot-check (session log path, cron ID, token row)
