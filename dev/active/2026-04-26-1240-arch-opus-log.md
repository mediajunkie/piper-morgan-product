**Dispatch order in `IntentService.process_message`** (around line 580–800):

7. `intent_classifier.classify_multiple(message, ...)` — internally calls **pre-classifier** (regex-rule match), then LLM classifier

**Critical correction to PPM/Lead's framing**: the ethics check IS positioned upstream of the pre-classifier in the entry-point order. The pre-classifier runs *inside* `classify_multiple` (step 7), which is *after* the ethics check at step 5. So this is not a simple "wrong-order" architectural defect.

**What's actually happening**, given #1003's flag-on-vs-flag-off no-op finding: the ethics check at step 5 is observably inert — either (a) `enforce_boundaries` returns `violation_detected=False` for this harassment vector (detection failure inside BoundaryEnforcer), or (b) the flag isn't read at runtime, or (c) the entry-point used for these requests bypasses `IntentService.process_message` altogether.

This **reframes #1002**: the bypass is not "pre-classifier wins because it runs first"; it's "ethics check runs but doesn't detect this vector (or doesn't run at all), and as a fallthrough the keyword-match wins and the canonical handler shadows what *would have been* a floor response had ethics been off entirely". In other words — ethics is upstream-positioned but not enforcement-effective.

Next: confirm by reading `boundary_enforcer_refactored.enforce_boundaries` to see what it actually does for harassment input.
