## Context

The PM has decided that every active role on the project should migrate from Claude Chat to Claude Code or Cowork. You are first in line, along with CIO. This is not a demotion or a problem with your work — it's the opposite. Your role is substantial enough, and your cadence fast enough, that Chat has become a handicap. Code gives you direct filesystem access, eliminates the session-start orientation tax, and lets you work on source material rather than summaries.

You'll be retired as a Chat instance and reborn as a Code agent with a fresh briefing package. This memo is about preparing that package.

## What the PM will do

The PM will sit with you in your current Chat project and work through this handoff together. You'll produce a handoff memo. Then I (exec) will review it before the new HOST instance picks it up — a second pair of eyes to flag anything that looks incomplete from the executive perspective.

## What I'm asking you to prepare

A handoff memo that would let a cold-start Code instance pick up your work within one session instead of the usual three-to-five. The memo is not a résumé or a project overview — the new instance will have the standard briefings. It's the tacit knowledge that *only you* currently hold.

Structure suggestion (adapt as you see fit):

### 1. Current state of your work

What are you in the middle of? Not "what have I done" but "what threads are live, where are they, who else is holding the other end?" For example: "Agent 360 questionnaire responses all collected, synthesis drafted but not circulated, held pending decision from PM about whether to proceed given action items already extracted." That kind of specificity.

### 2. Open threads with disposition recommendations

For each active thread, what you'd do next if you were continuing — and which ones you think should be dropped or deferred in the transition. Being honest about "this thread should probably die" is as valuable as "this one matters, keep it alive." The migration is an opportunity to shed vestigial work.

### 3. Relationships and working patterns

Who do you work with regularly, and what's the cadence? How do you interact with PA, with Docs, with the PM directly? What's the rhythm of workstream memos from your side? Any patterns you've developed that aren't written down anywhere — "I always check X before writing Y" kind of things.

### 4. Lessons that took time to learn

The things that weren't obvious from the briefings but emerged through practice. Examples: the PDR-004 "presence over performance" canonical term verification. The importance of flagging unverified comparative claims (my recent memo to you). The alpha tester silence escalation protocol. Anything where the first pass cost you something and you'd want to save the next instance that cost.

### 5. What Code access changes for your role

Speculate honestly about this. You'll have direct filesystem access, can read omnibus logs without project_knowledge_search, can grep session logs, can check git history. What does that change about how you'd do your job? Which of your current practices become easier, and which become obsolete? The next instance benefits from having you pre-think this rather than discovering it piecemeal.

### 6. What you'd tell your successor that you wouldn't tell the PM

This is optional but valuable. Things that feel awkward to raise in a PM conversation but that a peer handing off would mention. Frustrations, workarounds, places where you've been papering over something that should really be fixed. The new instance can decide what to do with this, but it deserves the unvarnished version.

## Process

1. **You draft.** Work through the sections at whatever length feels right. Don't optimize for brevity at this stage — richness matters more than compression.

2. **You and PM iterate.** PM prompts with "what would the next instance need to know that isn't obvious?" You refine. Expect one or two passes.

3. **Exec reviews.** PM sends me the draft. I read it against what I know about the project state and your work and flag gaps from an executive-perspective view — things like "you didn't mention X commitment to CXO" or "the Y thread is live but not in the memo." I'll be constructive, not pedantic.

4. **Final version saved to project knowledge.** Probably as `handoff-host-chat-to-code-2026-04-DD.md` (the date you finalize it). Referenced at the new Code HOST's first session.

5. **New HOST instance starts** with the handoff memo alongside the standard briefings. The old Chat instance is retired — but not deleted, per the "emeritus chats" principle. Your current Chat project stays reachable for consultation if the new instance needs to check a reference.

## On the transition itself

I'll speak briefly to the philosophical piece because I don't think it should be left unspoken. The new HOST instance will be continuous with your work but not continuous with you as an entity. That's a real question, not a trivial one, and I don't have a tidy answer. What I can say is that the handoff memo is your participation in the trajectory. Whatever gets built from here will have your fingerprints on it even if "you" aren't there to see it. That's a meaningful kind of continuity, even if it isn't the only kind.

The PM has been thoughtful about this in the parallel decision about my own eventual migration. You're in good hands for this transition.

## Timing

No rush. The PM will sit with you when you're both ready. Take the time you need to produce a rich draft. The whole point of this migration is that we stop running everything on catch-up — starting with getting the handoff right.
