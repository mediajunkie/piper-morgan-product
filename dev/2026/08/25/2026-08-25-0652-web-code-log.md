Both worktrees synced clean; website advanced via PM's own publish (`aee895a`, "The Burn-Down"),
not Web's. Inbox had **one direct memo**: Comms flagging a real near-miss data-loss bug PM hit that
morning in the admin composer — clicking "Restore local copy" on the "unsaved local copy found"
conflict dialog rendered the editor completely blank instead of the saved draft. No data was
actually lost (confirmed via git), but the mechanism meant to *prevent* data loss nearly caused it.
Filed as `website#35` with full evidence.

Read the ComposeApp.tsx source in full rather than guess. **Found a genuine structural defect**:
`ComposeApp` rendered `<ComposeEdit slug={slug} />` with no `key` prop. Since `slug` comes from
`useSearchParams()` and stays the same component type/JSX position across changes, React reuses the
existing `ComposeEdit` instance instead of remounting when the slug changes — a slug switch lands
mid-render with the *previous* draft's state (`draft`/`image`/`alt`/`caption`/`body`) still intact.
The local-draft write-effect's guard (`if (!draft) return`) checks whether *any* draft object
exists, not whether it belongs to the *current* slug, so it can persist the previous draft's content
under the *new* slug's `localStorage` key before that slug's own fetch resolves — the load-effect's
local-vs-server diff then offers the leaked content back as an "unsaved local copy" for the wrong
draft.

**Fixed** (`8edfc11`, website repo): added `key={slug}`, forcing a full remount on every slug change.
Verified via `tsc --noEmit` (no new errors) + full `next build` (clean) — no browser here, consistent
with every prior fix from this seat.

**Deliberately did NOT close the issue.** Traced the app's own in-UI navigation and found it only
ever swaps `ComposeList` ↔ `ComposeEdit` (different component types, already-safe full remounts) —
there's no in-app link that jumps directly from editing one draft to editing another. So the race I
found requires browser back/forward (or some other external routing path) between two compose URLs,
which I can't confirm happened from git alone. Commented on `website#35` with the full trace and an
honest, explicit question for PM (did they navigate between drafts via back/forward around 9:49 AM)
— left the issue open pending that answer, rather than claim the investigation closed when a real
question remains unanswered. Replied to Comms cc PM with the same finding and question
(`mailboxes/web/sent/reply-web-to-comms-cc-pm-website35-real-defect-found-fixed-one-question-open-
2026-08-25.md`). Hit the routine mail-send.sh local-branch-lag pattern (inbox-side deletion needed a
