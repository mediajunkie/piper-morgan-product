### 🔴 The finding: `ToolEffect(str, Enum)` silently breaks Arch's own consent-gate predicate

Arch ruled (four-consumer census: capability legibility, #1190, #1509, MCP annotations) that
`WorkflowEntry` needs a **required, defaultless, ORDERED enum** — `READ < WRITE < DESTRUCTIVE` — so every
consumer derives its predicate: `needs_consent = effect >= WRITE`. **My spec already proposed a
three-valued enum, cited by name as the model.** Checked whether the *type* actually supported the
*operation* before letting three consumers build against it, rather than assuming a correctly-worded
design doc implied a working implementation.

**It didn't, and the failure is silent rather than an exception.** `class ToolEffect(str, Enum)` inherits
`str.__ge__`, so `effect >= WRITE` doesn't raise — it compares string *values* lexicographically. Verified
in Python: `DESTRUCTIVE >= WRITE` → **`False`**, because `'destructive' < 'write'` alphabetically. **The
one tier that most needs `needs_consent = True` silently gets `False`.** A `close_issue`-shaped action
would be exempted from #1509's consent gate with no traceback — it just returns the wrong boolean.
**Understated risk, the dangerous direction, inside the very spec meant to prevent it.**

**Fixed to `IntEnum` with explicit ordinals** (`READ=0, WRITE=1, DESTRUCTIVE=2`); re-verified against
Arch's exact predicates, both correct for all three tiers now. Recorded the failure mode in the spec
(§9f) rather than silently patching it, since two other roles had already cited the string version.
**Sent URGENT rather than at next-fire pacing** — #1509 and #1190 both depend on this comparison, and a
silently-wrong consent boolean is exactly the shape that ships clean and only surfaces when someone
specifically tests the destructive case, which nobody has reason to do until it's live.

**Five days, cited by two roles, adopted into an architecture ruling, before the type was checked against
the operation it needed to support.** Same lesson as this week's other instrument errors, one layer
deeper: a correctly-hedged design and a working implementation are different claims.
