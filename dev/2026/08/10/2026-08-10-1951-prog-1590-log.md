### Seam chosen: `resolve_repo` path 3.5

Recovery lives inside `resolve_repo` between the env-var fallback (path 3) and the
`UnresolvedRepoError` raise (path 4). Reasons:

1. It is the ONLY point all seven GitHub surfaces share (see verify-first list). A thin
   wrapper would have to be adopted by each caller one at a time; the resolver is adopted
   already. #1342's `resolve_target` delegates to it, so the connector-agnostic seam
   inherits the fix for free.
2. Placing it AFTER the env fallback makes the change strictly additive: it fires only in
   the exact state that raises today. Every existing resolution outcome is bit-identical.
   Pinned by `test_env_var_fallback_still_wins_before_recovery` and
   `test_explicit_repo_short_circuits_before_any_recovery`.

### Guard: in-process, per-user, monotonic, 300s TTL

`_claim_recovery_attempt(key)` stamps `_recovery_attempts[key]` BEFORE any await, so the
live burst shape (ten unresolved resolutions in one window) costs ONE search, not ten.
Deliberately NOT `ContextCache`/#984: that degrades to a cache MISS when Redis is down,
which would disable the rate guard exactly when the system is least healthy. In-process is
the honest claim — at most one recovery search per user per worker per TTL.
`reset_recovery_guard()` is exported for tests / deliberate re-arm.

### Zero-repo user

Search returns `[]` (or a degradation) → INFO `default_repo_recovery_no_repos` including
whether it was a degrade → return None → caller raises `UnresolvedRepoError` exactly as
today. No scope question is ever asked (CXO item (i) preserved). The guard means the next
299 seconds of reads cost nothing.
