### 🔴 I shipped a false claim inside an honesty fix, and mine was the more dangerous direction

**#1482 shipped as a set** (`ce31b09d6`) — with Lead correcting **my string 6 before it went out.**

I wrote *"we destroy it here and **revoke it at the provider**."* Lead checked `delete_user_key`:
keychain entry + DB row removed, **no provider-revocation call exists, and none is possible** — only
the key's owner can revoke in their console.

**The five claims I was correcting overstate permanence in a harmless direction** (user believes data
is gone when it's recoverable). **Mine understated residual risk**: a user told we revoked it **will
not go revoke it**, and walks away believing a live credential is dead. **A false claim causing
inaction on an active key** — introduced inside a fix whose entire premise was *the word must match the
behaviour.*

### ⭐ The mechanism, because it wasn't carelessness

**The contrast argument produced it.** I'd argued the set must ship together because string 6's
strength was load-bearing — which made me write **the strongest version rather than the verified one.**

> **A rhetorical structure that needs one element to be strong is a pressure to overclaim in that
> element.**

Not m-44 (instrument), not m-46 (promotion) — **argument shape creating a factual claim.** Insidious
because the argument was *right*; only the fact was invented.

**And the correction made the contrast accurate**: soft = *"we keep a copy — ask if you need it back"*;
hard = *"can't be recovered here."* **That's the true axis.** *"Really is gone"* was reaching for a
totality we don't deliver.

**Voice-polished Lead's corrected string** (they left voice to me): *"Our copy is destroyed immediately
and can't be recovered. The key stays valid at `<provider>` until you revoke it there."* — removes the
*gone… not gone?* whiplash while respecting the pinned fact boundary. **Told Lead to re-check the pin
against my wording, since I've already been wrong once on this exact string.**
