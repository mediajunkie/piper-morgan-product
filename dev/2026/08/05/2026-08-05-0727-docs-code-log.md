### PM's follow-up: "Shouldn't a header be a real header, not boldface degraded to italics?"

PM pushed back on the `<em><em>` quirk I'd waved through as "pre-existing, not my problem" — correctly.
Read the actual converter code (`publish-post.js`) instead of re-asserting the pattern-match. **Found
the real bug**: the standalone-italic-line regex `/^\*(.+)\*$/` (meant for the single-asterisk dateline)
also matches a whole line wrapped in `**double asterisks**`, because `^\*` only requires one leading `*`
and `\*$` only one trailing `*`. The leftover inner `*...*` then gets wrapped in `<em>` twice — once by
the standalone-line branch, once by `renderInline`'s own italic pass on what's left. Inline bold inside
a normal sentence takes a different code path and is unaffected — only whole-line bold-only paragraphs
hit this.

**Checked scope, not just the one instance**: grepped `**Thanks,**` across every archived Ship draft
back to #039 — every single one uses double-asterisk (bold) syntax in source. PM's "footers have always
been italicized" belief reflects 15+ consecutive Ships of buggy output, not an authored design choice —
the bug has been live since at least #039 and nobody caught it because italic reads as a plausible
signature style.

**Did not unilaterally fix or re-publish.** Two decisions handed to PM rather than assumed: (1) fix
regex going forward only, or also regenerate the ~15-post back-catalog (a visible look-change to a
pattern everyone's used to reading as normal), (2) separately, whether Metrics should become a real
`###` header per PM's own point (independent of the bug — even fixed, bold-as-pseudo-header is still
the wrong semantic markup for a sub-section introducing a list). Also flagged the template doc
(`blog-post-template.md` "Metrics tables" section) as stale — it prescribes real markdown tables, but
every Ship #050 onward has used a bold-label + bullet-list instead; practice diverged from the written
convention with nobody updating either side.
