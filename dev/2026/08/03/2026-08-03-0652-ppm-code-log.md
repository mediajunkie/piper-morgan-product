### ⭐ The fix isn't a better predicate — it's GROUP BY

I could have sent `status IN ('bound','unreachable','stale')`, and I think that's the right set.
**I deliberately didn't**, because:

> **A filter encodes an assumption about which values matter. A grouping doesn't.**

Proposed stage 4 as a **status distribution** (`GROUP BY status`, counts only per HOST's aggregate
ruling). Three properties a filter cannot have: it **cannot return a misleading zero** (no-rows and
all-`unbound` are visibly different, where any filter collapses them); it is **robust to a status
value nobody anticipated** — which is the failure we just caught, one more time; and it **costs
nothing**. Generalised it cheaply: **for any cell whose predicate is uncertain, group rather than
filter** — the grouping degrades to the filter by summing, the filter can't degrade back.

### 🔴 And the status values exposed a third failure mode both models were blind to

`unbound` is the **default**, and `binding_repository.py:82` upserts the row with status set only if
explicitly passed — so **a row can exist for someone who started connecting and never finished.**

| state | meaning | fix it points at |
|---|---|---|
| no row | never entered the connect flow | onboarding / cold-start (CXO's hypothesis) |
| **row, `unbound`** | ⭐ **entered the connect flow and didn't finish** | **connect-flow failure — a THIRD fix** |
| `bound`/`unreachable`/`stale` | ever successfully connected | value-after-connection (the worse case) |

**CXO's binary had two cases; my funnel had five stages; neither could see "tried to connect and
failed."** Flagged as **conditional** — it only matters if `unbound` rows exist in prod, which I
can't determine from the default and the upsert alone. **The GROUP BY answers that in the same
query**, which is a third reason to prefer it.

Also caught a quieter version of the same bug: **`stale`/`unreachable` must count as connected.** A
tester who bound GitHub in July whose token has since lapsed **did** reach the moment CXO is asking
about; a `status='bound'`-only filter would undercount them as never-connected.
