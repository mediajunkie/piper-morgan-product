### #1466 — direction RATIFIED, two conditions, one affirmation

Lead asked a ruling-shaped question **before building**, which is the right time.

**✅ Direction is right**: mint-in-Piper / redeem-in-Slack — the **authenticated** side initiates, the unauthenticated side redeems by proving it holds the code, and **Slack never holds a Piper credential.** The reverse would let an unauthenticated Slack user mint. **ADR-070's identity boundary satisfied by construction** (`owner_id` FK + `unique(slack_user_id, slack_team_id)` prevents one Slack identity resolving to two owners — the direction that matters). And **`consume_invite_token` is the right reuse**: atomic `UPDATE … WHERE used_at IS NULL`, *"never a separate check-then-write"* — **single-use by construction, TOCTOU-free**, the inverse of the `check-branch` defect I ruled on 7/29.

**🔴 Condition 1 — the code spec contradicts the shape it cites.** Design says *"6-digit code (invite_tokens shape)."* **Verified against source**: `generate_invite_token()` is a **24-char Crockford Base32 token via `secrets.choice` — ~120 bits. A 6-digit code is ~20.** And it's redeemed over an **unauthenticated channel**, so the space is *online*-attackable. Either choice is defensible; **the citation being wrong is not.** Inherit the generator (free), or keep 6 digits for DM-typeability **with bounded attempts per user AND per team as a requirement**. My lean is the latter — but **in the design before build, not discovered during it.**

**🔴 Condition 2 — the re-link conflict path is unspecified**, and it's exactly where linking flows fail. A second redemption from an already-linked Slack identity hits the unique constraint. Three outcomes: ❌ silent no-op (user believes they linked, didn't), ❌ takeover overwriting `owner_id` (**an account-linking vulnerability** — anyone with a code could rebind someone else's Slack identity), ✅ **fail-closed: refuse + honest message + explicit unlink-first path.** *A constraint violation handled by "whatever the ORM does" is the silence class we've spent two weeks eliminating.*

**✅ Condition 3 — promoted Lead's planned crash-path fix from rider to requirement**: unlinked → honest decline, **never a default owner**. Confirmed the defect is live at `response_handler.py:605-614` (`user_id=slack_user_id` — a Slack id where a Piper UUID is expected), so **unlinked-user is the normal case, not an edge case.**

Endorsed the plumbing/copy division — strings in decline/confirm tables rather than code paths is the correct seam, same shape as ADR-066 D7.
