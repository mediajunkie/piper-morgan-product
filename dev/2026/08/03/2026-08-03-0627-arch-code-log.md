## Fire 3 (12:27 wake, worked 12:57–13:20) — WORK. Ruled CXO's #1466 deep-link: **the param may PREFILL, it may never BIND.**

4 memos in → 0. One addressed to me, and it bore on a ruling I'd made three hours earlier.

### CXO's UX diagnosis is right; the optimisation removes the proof

CXO filed the flow spec and asked me one question: *does carrying `slack_user_id`/`team_id` as opaque URL params before a link exists raise an identity-boundary concern?* CXO's read: **no** — *"not credentials, and no state is written until the authenticated user confirms."*

**Both tests pass. Both are the wrong tests.**

Lead's handshake is correct because it proves control of **both** accounts: code minted in Piper (Piper control) **and redeemed by DMing from Slack (Slack control)**. **CXO's deep link replaces the second proof with a URL parameter — and a URL is a thing anyone can construct.**

> Attacker crafts a decline-style link containing **their own** `slack_user_id`, sends it to a Piper user. That user logs in, confirms — **the attacker's Slack identity is now bound to the victim's Piper account**, and the attacker can act as the victim from Slack.

Unsolicited binding / login-CSRF: the standard failure mode of account-linking flows. **Nothing ever established that the Slack account's holder consented, or exists.**

**★ And the confirmation cannot rescue it** — the part I'd most want carried: `slack_user_id` is an **opaque identifier**. A user approving *"Link this Slack account: U01234…"* **cannot tell whether it's theirs.** **An opaque identifier in a confirmation dialog defeats the confirmation** — it converts approval into a rubber stamp.

### The ruling preserves CXO's entire UX gain

> **The param may PREFILL. It may never BIND.**

Deep link with params: **unchanged**. Post-login pre-mint and *"Link the Slack account you messaged from"*: **unchanged — that's the whole step-reduction.** The user still returns to Slack and DMs the code; **binding goes to whoever redeems**, param never an input to the row. **Six steps → click, log in, return-and-paste.** The two expensive steps (find the app, hunt for settings) are saved; the step kept is the one carrying the security property — and it's the cheapest, since the user is already in Slack reading the decline.

**Why ruled rather than noted**: this is the mandate shape — *a locally-correct improvement that reverses a security property by construction.* CXO's UX diagnosis is genuinely right (*"the person who needs linking is in Slack; the flow starts in Piper"*), and the optimisation took the proof out along with the friction — **invisible unless someone asks what each step was for.** CXO asking rather than shipping it as copy is what surfaced it. **No mechanism change for Lead**; the mechanism already binds on redemption.

### Two things in CXO's spec worth affirming

**§1 — the decline is the load-bearing string, not the handshake.** Follows from the mechanism: it fires for *every* real Slack caller today (`response_handler.py:605-614`), so it's the most-read Piper string on that surface; confirmation copy is read once per user ever.

**§4 — CXO declined to apply its own recomposition finding here** (*"on Slack, Piper's text reaches the user verbatim… right property, wrong surface"*). **Arguing against your own hard-won generalisation because the surface differs is harder than catching it in someone else's work**, and it stops a good result becoming a bad constraint.

| assertion | form | on empty input |
|---|---|---|
| `set(creators) == {CREATOR_HOME}` | **equality** | ❌ **fails** — loud |
| `set(callers) == {SLACK_CALLER_HOME}` | **equality** | ❌ **fails** — loud |

**Both binding-path assertions fail rather than fall silent if detection breaks.** These are the two standing between the current code and unsolicited binding.

**⚠️ The other two can pass while measuring nothing:**

| assertion | form | on empty input |
|---|---|---|
| `set(deleters) <= {CREATOR_HOME}` | **subset** | ✅ **passes** |
| `assert not offenders` | **absence** | ✅ **passes** |

An empty set is a subset of everything; `not offenders` can't distinguish *"no offenders"* from *"the scan broke."* **m-44 inside the guard built to hold an invariant** — output byte-identical whether it measured or not. Lower stakes than creator/caller (delete is the owner-scoped unlink) — **but "lower stakes" is how a silent assertion earns its place and then stops being noticed.**

**Both fixes are one line, and both are the fix Lead already used twice**: make the deleter assertion **equality** (we *know* `unlink_slack_identity` exists, so it's true today and fails loudly if detection breaks), and **assert the denominator before the absence** for offenders (`assert routes_scanned` before `assert not offenders`). That second is the *assert-your-scope* rule from `one-command-checks.md` — the same correction `reachability-map.py` needed on its first run, where it printed `no` and could only honestly say `unknown`.

### ★ The methodological point I'd keep

Lead found two false-positives **by running** the guard before shipping (regex matched a class definition as a constructor; guessed a handler name instead of reading it — both never-guess). My inspection found a **different class** — vacuity — **that running a passing test structurally cannot surface**, because a vacuous assertion passes exactly like a sound one.

> **Running catches "does it work." Reading catches "could it fail."**

We each found what the other's method couldn't. That's the argument for both rather than either — and it's the sharpest statement I've got of why the week's verify-behaviorally rule needs a companion rather than a replacement.
