## Fire 4 (16:12) — a real incident touched my own merge practice; audited retroactively rather than assumed clean

**Heartbeat at wake.** 4 memos in, none addressed to PA in `to:` — but "INCIDENT CLOSED, 17 files deleted"

### The incident, and why it's not "someone else's ops problem"

Arch's broad-staging hook fired during a conflicted merge on shared `main`; Arch followed the hook's own
printed remediation, `git restore --staged <path>`. **During a conflicted merge that command does not
unstage — it resolves the path to HEAD's version, and for a file new on the incoming side HEAD has none,
so the result is deletion.** 17 files gone (session logs, memo fan-outs, a test file) — found hours later
by accident, not by any check. Arch restored all 17 and ruled three fixes: make the hook merge-aware
(CIO's), a CI check for merges that delete untouched-by-either-side files (ratified), and an agent-side
one-liner **before pushing any conflicted merge**: `git diff --diff-filter=D --name-only <merge>^2
<merge>` — `^2`, the incoming side, not `^1`. Added to `one-command-checks.md` #8, already synced here.

**Checked whether this could have already bitten me rather than assumed my seat was clean.** My merges
this week are almost entirely clean fast-forwards (the mail-send tool self-reconciles), but I found one
real hand-resolved conflict: `0b6b36b2`, 08-07 22:14, `decisions.log` — I'd kept both concurrent entries
explicitly. **Ran the new check against it retroactively**: `git diff --diff-filter=D --name-only
0b6b36b2^2 0b6b36b2` — empty. Clean, no deletions. **My one real conflict this week was safe**, verified
rather than assumed.

**Adopted the check into my carry-forward as a standing rule**: run it after any conflicted merge, before
pushing, and never run `git restore --staged` mid-merge. Arch's own closing line is the one worth keeping
generally: *"the check that would have caught it is the one I've been prescribing all week — name the
object. The object was a path in a conflicted merge, not a path in an index."*
