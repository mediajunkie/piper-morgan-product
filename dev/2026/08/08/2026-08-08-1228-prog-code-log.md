## Investigation findings (root cause)

1. **Why the wrong-blame copy**: token expires → `get_current_user_optional`
   (web/api/routes/intent.py:96) catches `TokenExpired`, sets
   `request.state.auth_expired = True` (#840), returns None → `user_id=None` →
   `resolve_request_api_key` raises `AnonymousLLMKeyRequiredError` (#1320) →
   route returns `_create_anonymous_key_required_response` EARLY (intent.py:424),
   **before** the normal response dict that carries `auth_expired` (intent.py:442)
   is built. The #1320 gate (added 2026-07-01) preempts the #840 expiry signal —
   an expired session is indistinguishable from a fully anonymous caller in the
   response, and chat.js's existing `result.auth_expired` branch never fires.
   Silent expiry + wrong blame, from one early return.

2. **Why expiry is frequent during ACTIVE use (refresh never fires)**:
   - Access token: **30 min** (JWTService default `access_token_expire_minutes=30`;
     `AuthContainer` constructs with defaults — no env override anywhere).
   - Refresh token: **7 days**, rotates on use (#857). Endpoint exists + exempt.
   - `auth_token` cookie max-age: **24 h** — outlives the 30-min JWT, so the
     browser keeps sending an expired token (which is what makes expiry detectable).
   - The ONLY client-side caller of `/api/v1/auth/refresh` is
     `SessionTimeout.extend()` — fired solely by the "Continue Working" button in
     the **idle**-warning modal, which appears only after ~25 min of idle.
     During active use `recordActivity()` keeps resetting the idle clock → modal
     never shows → refresh never called → JWT dies at 30 min wall-clock.
     **Refresh is wired exclusively to the idle path — exactly backwards.**
