### Fix
- `services/mcp/consumer/github_adapter.py`: added
  `GitHubMCPSpatialAdapter.probe_issue_connector` — a tri-state existence
  probe (`"found"` / `"not_found"` / `"unknown"`), mirroring
  `get_issue_connector`'s resolve → bound-binding → `issue_read` call shape
  but classifying instead of collapsing. `"not_found"` requires POSITIVE
  evidence (`_is_not_found_text` on the content or an exception leaf — the
  SAME check #1858's write-verification readback leg uses); every
  degradation or other erroring/unparseable result is `"unknown"`, never
  inferred as not-found. Added a number-presence guard (`item.get("number")
  is not None`) before trusting a parsed payload as "found", so a real
  issue whose title happens to mention "404" is never misclassified, and
  the #1858-class in-band JSON error body (valid JSON, no number) still
  falls through to the not-found text check instead of reading as a
  degenerate "found".
- `services/intent_service/destructive_confirm.py`: `build_close_reopen_confirmation`
  now calls the probe instead of `github_router.get_issue`; dropped the
  `GitHubIntegrationRouter`/`is_available()` check entirely (the probe's own
  binding check covers "not connected" as `"unknown"` → fallback, same end
  state, fewer moving parts). Added an explicit no-principal guard
  (`_principal_from_intent(intent) is None → fallback`) — needed both for
  AC #7 (reads must use the acting user's own connection) and to satisfy
  mypy (the probe's `user_id: str` param rejected the `Optional[str]`
  principal without a narrowing guard).
