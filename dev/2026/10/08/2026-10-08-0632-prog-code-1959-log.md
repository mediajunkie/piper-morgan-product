## Progress

### Investigation
- Traced the live repro: the #1190 gate's generic `build_confirmation_offer`
  arms "Close issue #N? (yes/no)" on the number alone (no lookup). On "yes"
  the handler (`_handle_close_issue_query`) skips its own preview fetch
  (`destructive_confirmed` context marker) and calls `update_issue` directly;
  for a nonexistent issue this raises `GitHubIssueNotFound` (#1858, raised
  ONLY from the connector write-verification leg in
  `GitHubIntegrationRouter._try_connector_write`), caught by
  `_unverified_write_result`, producing the "There's no issue #N..." reply —
  one turn too late.
- Confirmed there is no pre-existing "definitive not-found" signal on a pure
  READ anywhere in the codebase (`get_issue`/`get_github_issue_direct`
  collapse 401/403/404/network-error all to `None`; the #1858 not-found flag
  only exists on the two-leg WRITE verification). Decided NOT to extend the
  connector/adapter layer for this (out of the stated scope and a bigger
  surface than the issue asked for). Instead: resolve the repo EXPLICITLY
  (never let `get_issue` resolve a default internally) so that a clean
  `None` back can only mean "repo confirmed, nothing at that number" — never
  "no repo resolved". That satisfies AC #6's three enumerated fallback
  conditions (repo unresolvable / GitHub not connected / read errors)
  without inventing new adapter-layer plumbing.
