## 4. Cross-family notes

**#1920 cross-family release rule** (`services/intent_service/inversion_live.py:655-829`): a reminder/todo carrier (`handle_reminder_task_turn`, `handle_ftux_interview_turn`) releases on a router-named operation whose `ACTION_REGISTRY` category differs from its own (EXECUTION) **only if that operation has a rail entry** — `entry = get_action_workflows().get(op); if entry is None: ... return None` (`inversion_live.py:804-813`). Because `manage_portfolio` has **no rail entry** (§1), it is currently **structurally excluded** from participating in the #1920 release path at all — any router call naming `manage_portfolio` against a todo/reminder carrier is logged `armed_carrier_read_release_declined, reason="not_rail_dispatchable"` and the carrier stays bound. This changes the moment any of its WRITE/DESTRUCTIVE branches get split into real rail entries per Arch's ask: a PORTFOLIO-family write (archive/add/restore, and delete if ever wired live) would then become eligible to cross-family-release an EXECUTION-family carrier turn, same as `delete_todo`/`clear` already do today. Worth flagging to Arch/CXO as a consequence of the split, not a reason against it.

**Duplicate/overlapping branch with an existing rail entry**: Row 2 (list archived, `canonical_handlers.py:4414-4428`, `4548-4580`) functionally duplicates `run_archived_projects_query_workflow` (`services/intent_service/workflow_entries.py:841-938`, registered at `workflow_entries.py:2673` as the `list_archived_projects` rail entry, shipped under #1570/#1431). The rail entry's own docstring (`workflow_entries.py:846-863`) says it exists BECAUSE the in-handler branch "never ran" for the STATUS-routed phrasing that triggered #1570 — but the in-handler branch still exists and still runs for any message that reaches PORTFOLIO/`manage_portfolio` with an "archived" token. Two live code paths produce the same effect (READ, same `PortfolioService.list_archived_projects` call) for overlapping input. Not itself an effect-class ambiguity, but worth noting since a READ-rail-adapter split (per Arch's §3 `get_current_time` precedent) might obsolete Row 2 entirely rather than adapt it.

- `services/process/adapters.py:28` (`OnboardingProcessAdapter`) is commented out of the registry (confirmed by the comment at `canonical_handlers.py:4469-4471`: `# registry.register(OnboardingProcessAdapter())` — not live).

## 5. Open questions for Arch

1. **Row 4 (delete) is the sharpest effect-class ambiguity.** As currently wired, "delete my project X" never deletes anything — it only ever returns a confirmation prompt, and nothing in the codebase consumes the `awaiting_confirmation`/`project_id` context on a later turn to call `PortfolioService.delete_project(confirmed=True)`. So by *current, live behavior* it is READ (composes a message, mutates nothing). But the service method it's clearly meant to call one turn later (`portfolio_service.py:354-416`, `project_repository.delete()` — a hard delete, no restore path, unlike archive) is unambiguously DESTRUCTIVE once reachable. **Which does the split take as its unit**: the branch as it behaves today (READ, dead-end), or the branch as its comments/docstring/intent describe it (DESTRUCTIVE, pending a second-turn wire-up)? This also means the rail split and the "wire up the confirmation loop" fix are coupled — splitting now without fixing the dead path either ships a DESTRUCTIVE-labeled entry that still can't destroy anything, or ships it READ and someone has to remember to re-label it when the wire-up lands.
2. **Rows 8/9 (add-flow's onboarding-session writes) mutate conversation/session state, not portfolio domain data.** Is a `PortfolioOnboardingManager` session transition (`GATHERING_PROJECTS` → `DECLINED`, or session creation) in-scope for "WRITE" under the rail's `EffectClass`, or is `EffectClass` meant to describe only domain-table mutations? If the latter, rows 8/9 might belong with Row 1's READ class instead (no portfolio data is touched) despite literally calling `.create_session()`/`.transition_state()`.
3. **Row 12 (the update/edit literals' dead end) — is this a known gap or new information?** `pre_classifier.py:1151-1152` recognizes "update my project" / "edit my project" as PORTFOLIO/`manage_portfolio`, but the handler has no corresponding branch; those messages silently fall to the generic "I can help you manage your projects…" help text. I found no issue number attached to either literal's comment acknowledging this. Confirm whether this is intentionally parked (and if so, whether the two literals should be removed from `PORTFOLIO_PATTERNS` under the routing moratorium's "dead claim" logic) or is a genuine, previously-unnoticed gap.
4. **Row 2 / the `list_archived_projects` rail-entry duplication** (§4): should this inventory's split retire the in-handler branch (point `PORTFOLIO_PATTERNS`'s archived-list literal fully at the existing rail entry) rather than give it its own new READ adapter, since a working rail READ already exists for the identical effect?
5. **The question-form corpus rows** ("what are my projects?", "what projects am I working on") — I could not trace, within this handler's own branches, how `PORTFOLIO_LIST_PATTERN`'s imperative-shaped regex (`show|list|view`) ends up claiming interrogative phrasings. That match is presumably happening upstream of `pre_classify` (normalization/rewrite) rather than inside any `manage_portfolio` branch, so it's out of this inventory's scope by construction — flagging in case it matters to how the split's corpus evidence is read.
