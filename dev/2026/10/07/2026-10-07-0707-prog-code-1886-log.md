**The branch-3-without-re-entering-the-handler problem** (task's point 3).
A FULL restatement ("add project" again, or "add project Foo") matches the
same detector regardless of whether a name follows. The task's own spec
says a full restatement releases unconditionally — but releasing a BARE
no-name restatement would land back in `_handle_add_project` fresh (no
pending offer, since the pop already happened), which has no memory of the
first ask and would render the IDENTICAL `_ADD_PROJECT_ASK` text again —
exactly the double-prompt the issue is about. Resolved WITHOUT a stored
marker: the restatement branch in `handle_add_project_name_turn` checks
`extract_add_project_slots(text)` on the restated text itself — if it
carries a name, release (→ create via the ordinary path); if it doesn't,
answer the branch-3 copy directly, right there, never releasing. Verified
behaviorally that a second bare "add a project" during the carrier's turn
gets the "sorry for the loop" copy and does NOT re-emit the ask (test
`test_bare_restatement_gets_branch_3_copy_without_releasing`).

**Off-intent release had to be narrowed from a literal mirror.**
`PreClassifier.pre_classify` claims almost any utterance merely mentioning
"project" as `manage_portfolio` with no slots (`PORTFOLIO_PATTERNS`) —
confirmed empirically: `is_plausible_project_name("this is not the name of
the new project at all")` → `True` (would wrongly create a project with
that literal name if not intercepted), AND
`PreClassifier.pre_classify(...)` → claims it as `manage_portfolio`. A
literal mirror of `handle_reminder_task_turn`'s off-intent release (release
on ANY pre-classifier claim) would release this straight back into
`_handle_add_project` fresh with the same no-name text — same double-prompt
bug, different trigger. Fixed by excluding the carrier's OWN family
(`manage_portfolio` / `add_project`) from the release condition — only a
claim OUTSIDE that family counts as a genuinely competing command. This is
a one-line, reasoned deviation from "mirror EXACTLY," documented in-code and
here; I did not invent a new mechanism, I scoped an existing one correctly
for a family-overlap case the reminder-task carrier doesn't structurally
have (its own family's `REMINDER_PATTERNS` were tombstoned in #1595 Phase 3,
so this collision class can't currently occur there).

**Known, accepted residual gap (not introduced by me, inherited from the
mirrored design):** `PreClassifier.pre_classify` no longer claims most
product commands at all post-#1595-Phase-3 deletions (e.g. "close issue
108" → `None`; `GITHUB_QUERY_PATTERNS` was tombstoned to `[]` 2026-10-02).
The reminder-task carrier's own docstring claim that the pre-classifier
"claims every product command tried" is now stale, and its #1899
`read_op_claims_turn` second-oracle only covers READ operations, not
DESTRUCTIVE ones like close/reopen. So a destructive-command collision
("close issue 108" stated while the add-project ask is pending) would, in
both carriers, get bound as the answer rather than released — a
pre-existing, documented limitation of the mirrored idiom, not a new defect
from this change. Flagging it rather than quietly building a stronger
discriminator, since the task's instruction was to mirror, not to improve
the off-intent coverage (that's `TestExtractionPatternRatchet` /
corpus-deposit territory per CLAUDE.md, out of scope here).
