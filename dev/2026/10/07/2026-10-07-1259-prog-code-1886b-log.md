## New module

`services/intent_service/armed_turn_consult.py` — `classify_armed_reply(text,
user_id, *, session_id, intent_service) -> ArmedReplyDecision`
(`ArmedReplyOutcome.RELEASE/BIND/CONFIRM`). Calls
`inversion_router.route(text, None, llm_service=..., grammar=..., user_id=...)`
— the SAME stateless call shape `inversion_live.read_op_claims_turn` already
uses (not `consult_inversion_live`'s session-threaded one).
**Deliberately NOT gated on `PIPER_INVERSION_LIVE_CATEGORIES`** — that flag
governs what may DISPATCH live; this consult never dispatches, so gating it
would leave the #1886 bug unfixed on any deployment that hasn't flipped a
category live yet (exactly backwards). Added to
`TestInversionShadowNoExecutionBoundary.ALLOWED_REFERRERS` in
`tests/test_architecture_enforcement.py` (named-file addition, same
precedent as `inversion_live.py`).

## Deviations from a literal reading, with reasoning

1. **Scope of "REMOVE the manage_portfolio/pre-classifier-based release
   test"**: read as applying to BOTH carriers' pre-classifier-based release
   (not just add_project's), because (a) Arch's own framing — "two copies of
   'release or bind' are how they drift", "this isn't a special case; it's
   the first instance of the general one" — argues against leaving the old
   mechanism in place beside the new one in either carrier, and (b) the task
   brief explicitly asks for a reminder-task outcome-3 fallback, which only
   has teeth if outcomes 1/2 are ALSO reached via the new consult there.
   Flagging this reading explicitly since the literal sentence names only
   the `manage_portfolio` exclusion.
2. **Reminder-task CONFIRM fallback**: no yes/no confirm copy exists for
   "save this as a reminder?" (only destructive DELETE confirms and the
   generic, non-reminder-specific `consent_gate.build_consent_check_offer`
   exist, and both would need re-dispatch through the ORIGINAL message text
   — fragile here, since the already-resolved `task_text`/time would be
   lost). Per the brief's explicit permission ("mirror ... with the
   reminder's own existing confirm/clarify idiom if one exists" — CLARIFY is
   named as an acceptable alternative to CONFIRM), outcome 3 reuses the
   carrier's own existing re-ask (`_task_reask`) verbatim — no new copy
   invented, nothing written either way.
3. **Add-project CONFIRM's "yes" does not go through the generic #1190
   `CONFIRM_PENDING_ACTION_WORKFLOW`/Intent re-dispatch** (destructive_confirm.py's
   mechanism) — verified that re-dispatching `action="add_project"` would
   re-extract the name from `original_message` text (`run_add_project_workflow`
   → `_handle_add_project` → `extract_add_project_slots`), which would NOT
   recover an answer-turn's bare name ("Klatch") since it isn't phrased as
   an imperative. Per the brief's explicit instruction ("'yes' creates via
   the existing shared create helper"), the confirm's own turn handler calls
   `_create_or_report_project` directly with the already-known name/repo.
