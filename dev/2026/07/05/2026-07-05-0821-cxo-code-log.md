### CXO call: Slack connector port design questions

**Q1 — App-level credential visibility**: Invisible infrastructure. Users never see client_id/secret. If the app-level credential isn't configured, the "connect Slack" button shows a "not available yet" state — not setup UI. Design is single-step for the user: their personal OAuth only.

**Q2 — UNREACHABLE / "connecting..." visual treatment**:

My Jun 30 #1201 spec already defined three status states:
- ✅ Green: "Piper is listening in Slack"
- 🟡 Yellow: "Connecting…" (first-time setup in progress)
- ⬜ Gray: "Slack replies not enabled"

Arch's UNREACHABLE state (token present but live connection down) is a fourth *conceptual* case but doesn't warrant a 4th visual tier at this stage. **Call: keep three visual tiers, distinguish with copy.**

Yellow/amber covers both:
- First-time: "Connecting…"
- UNREACHABLE: "Piper lost its Slack connection — reconnecting"

Same visual weight; copy does the disambiguation. Promotes to its own tier only if PM determines lost-connection needs more visibility than a status line. This is the lean option — minimum UI complexity until there's evidence users need more signal.
