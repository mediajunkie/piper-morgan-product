**Investigation, not assumption.** Lead's memo proposed two hypotheses: (1) the banner/footer/frontmatter prose date fields don't advance consistently, (2) agents in ephemeral worktrees read a stale local copy without syncing first. Both plausible, but before acting I read the actual `.claude/hooks/session-start.sh` code rather than trusting either hypothesis at face value — and found a third, more structural mechanism neither Lead nor I had named yet: the hook's own staleness check uses `stat -f %m` (raw filesystem mtime), which is fundamentally decoupled from git content history in a multi-worktree setup. `git worktree add` stamps every file with a fresh "now" mtime at checkout regardless of when its content last changed; a long-lived worktree's on-disk mtime for a file it hasn't happened to re-touch just reflects whenever it was last synced, not when the content was last updated on origin. This is the mechanism that actually TRIGGERS the "tell PM it's stale" behavior — the hook is what fires the flag an agent then acts on.
