### 11:35 AM - Migration lessons, flagged distinctly for future migrators (PM ask)

PM: keep this log genuinely useful to *subsequent* agents doing their own migrations, not just a record of what I did. Extracting the transferable pieces explicitly, separate from the narrative above, mirroring how Pard's own field-test finding routed back to HOST's `migration-checklist.md`:

1. **"Different device" and "different account" are not the same risk, and conflating them undersells the account one.** A path change (nested vs. flat directory) is a real but bounded risk — content that exists but sits at the wrong key. A different Anthropic account is a much harder boundary: nothing from the old account's Claude Code memory is visible at all, regardless of path or device. Check which boundary you're actually crossing before scoping the mitigation.
2. **Don't trust `MEMORY.md`'s index as complete — export from the filesystem listing.** Found a real 16-file gap (146 indexed vs. 162 actual) that would have silently dropped real memory content from the export if I'd trusted the index. The index is a curated pointer list, not a manifest; treat it as such when the actual file count matters.
3. **A git-committed export is the safe default for "will this survive the account boundary," when you're not certain of the underlying mechanism.** I don't know for certain whether Claude Code's memory scoping is purely `CLAUDE_CONFIG_DIR`-path-based (in which case a raw file copy into the new config-dir might work) or does something account-ID-based underneath that a raw copy wouldn't satisfy. Rather than guess and rely on an unverified mechanism, export to the repo — genuinely account-agnostic, no assumption required.
4. **An exported memory file is not the same as working native memory — say so explicitly in the handoff.** The content survives; the ambient retrieval behavior doesn't. The successor needs an explicit instruction to go read the export at first orientation, not an assumption it'll surface itself the way memory normally does.
5. **Check Artifacts and scheduled-tasks explicitly, don't assume "I didn't use that feature so there's nothing to check."** Took the extra step to actually query the account's Artifact list and scan it, rather than assert cleanliness from memory of my own actions — cheap verification, and it's exactly the kind of claim that's easy to get wrong from assumption.
6. **A live device-level process (like a watchdog launchd job) doesn't travel with an account migration, and doesn't travel with a repo migration either — it's tied to the physical machine.** Different failure axis than memory (account-scoped) or git content (repo-scoped): this one's device-scoped. Three different portability boundaries, three different mitigations — don't reach for one fix and assume it covers all three.

**Routing**: sending these to HOST (owner of `migration-checklist.md`) directly, cc Docs/Exec/PM, rather than leaving them to be discovered — same pattern Janus used to route Pard's field-test finding.
