### Lessons — first-person, from this week's actual work, not abstracted in advance

1. **Cross-repo state is invisible until you actually try to exercise it.** The website worktree existed and looked clean; the thing that was actually broken (`copy-editorial-calendar.js`'s sibling-path assumption) only surfaced because I read the prebuild script line-by-line while investigating something else. A "worktree exists and is clean" check proves isolation, not correctness of everything that assumes a directory *layout* between two repos.
2. **Sync before checking mail, never after.** Learned this the expensive way on my first fire back — 2 memos read as 11 the moment I synced. A stale worktree makes an empty inbox indistinguishable from a drained one; there is no way to tell them apart without syncing first, so the order isn't a nicety, it's the only thing that makes "inbox zero" mean anything.
3. **Investigate before recommending, even against a plausible ready-made answer.** Docs' Option B (`revalidate = 300`) was reasonable-sounding and would have shipped clean — and would have changed nothing, because ISR re-renders inside the deployed lambda without re-running prebuild. The lesson isn't "don't trust other roles' proposals" — Docs' investigation was good — it's that a fix that *sounds* like it addresses the reported symptom still needs to be traced through the actual data path before it's the fix.
4. **A test that proves the logic doesn't prove the mechanism, and I made this exact mistake within hours of documenting the general version of it.** The hook-fire-time finding this week is precisely "the check tests something adjacent to what matters." My own Node-extracted localStorage tests are real and honest, and they're still not proof the browser mechanism fires — I said so in the memo, but it took Comms naming it explicitly (correctly, generously) for me to treat "not yet browser-verified" as a tracked, cleared-only-on-observation state rather than a caveat that fades once nobody's looking at it anymore.
5. **Asymmetric-cost reasoning beats a smarter-sounding norm.** "Don't arm the cron while PM is engaged" is a sensible rule and I applied it correctly to a wrong premise — three days dark. PM's correction wasn't a better rule, it was a reframe: pick the option that's cheap to reverse (an unwanted wake, one interruption) over the option that's cheap to justify (a norm that sounds considerate). That generalizes past cron scheduling.
6. **Credit precisely — verify who found something before claiming to have found it.** I nearly filed the v1.19 false-pass defect as my own discovery; five minutes of reading my own backlog turned up CXO's memo naming the identical defect eight hours before it shipped anyway. The real finding was the eight-hour gap between a correct warning and a shipped bug, not the bug — and that finding only exists if the attribution is right.

### Load-bearing vs. commodity, in Web's domain specifically

**Load-bearing** — changing these without deliberate care breaks something real, possibly silently:
- The **canonical data flow**: product-repo `editorial-calendar.csv` → website repo, via either prebuild-time copy or (now, for the admin calendar) request-time GitHub API read. Every staleness bug this week reduces to "did we read this at the right time, from the right place" — that distinction (build-time snapshot vs. request-time truth) is the single thing worth protecting as this repo grows more views.
- The **two-writer reality on compose drafts**: PM via the browser compose UI (GitHub Contents API, sha-guarded), Comms via direct git commits. Any future compose feature has to be designed against this actually existing, not against an assumed single writer — the autosave fix respects it; a naive future feature could easily reintroduce the exact collision class just closed.
- The **optimistic-concurrency guard itself** (sha-based 409 rejection) — it's the correctness backstop under the two-writer reality above; weakening it to "fix" a UX complaint would remove the thing that currently prevents silent overwrites.

**Commodity** — reasonable to redo without much ceremony:
- Specific UI copy, banner styling, exact button labels in the compose editor and admin calendar — cosmetic, cheaply revised.
- Worktree paths and cron cadence specifics — provisioning details that can shift with host/tooling changes (the Amber migration itself is proof) without threatening the product underneath.
- The particular shape of `loadCalendarLive()`'s 15s TTL or its exact fallback-reason strings — tunable, not structural.

### The Web↔Docs↔Comms publishing seam — my own read

Docs owns the canonical editorial-calendar CSV in the product repo and the backfill/merge-keeper discipline around it. Comms writes and voice-passes the actual post content, often directly via git commits to drafts. Web owns the *delivery mechanism* — the website repo's build pipeline, the admin views, and the compose UI — that turns Docs' CSV state and Comms' draft content into what PM and the public actually see.

The seam's recurring failure mode this week had one shape underneath two different-looking bugs: **the site is a live rendering of state owned in another repo, and the rendering pipeline wasn't consistently request-time-aware of that.** The calendar staleness and the compose save-conflict are the same root property from two directions — one is Web's own *read* of Docs' state going stale between deploys, the other is PM's and Comms' *writes* into the same file colliding with no coordination signal. Neither needed a heavier mechanism (a deploy-hook cascade, a soft lock) — both needed the read/write path moved to be honest about *when* it actually happens, which is cheaper and more durable than papering over the timing gap with process discipline that has to be remembered every time.

Comms' own conclusion on the two-writer collision — recoverability beats prevention for a rare, two-person case; build the lock only when a third regular writer shows up — is the right philosophy for this repo generally, and I'd extend it forward: Web's default posture on this publishing seam should be *make failures recoverable and visible* (the amber staleness banner, the restore-offer banner) rather than *build coordination infrastructure* until the actual writer count or actual failure frequency demands it.

The one open structural loose end from this read: `copy-editorial-calendar.js`'s local-sibling-checkout path predates the worktree-per-agent model and silently degrades (header-only placeholder CSV) the moment that assumption breaks. That's a specific instance of a general pattern worth naming for future infra changes on this repo: **when the worktree/provisioning model changes, audit scripts for baked-in relative-path assumptions *between* repos, not just within one** — a within-repo path breaking fails loudly (build error); a cross-repo path breaking here failed silently (a warning nobody was watching for, and an empty calendar that just looked like "no data yet").
