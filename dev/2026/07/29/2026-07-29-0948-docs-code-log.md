```

git -C …/piper-morgan-website config --local user.email  → rc=1 (unset)
git --global user.name / user.email                      → unset
```

Effective identity in the website docs worktree resolves to git's **hostname auto-derivation**:

```
$ git var GIT_AUTHOR_IDENT
xian <xian@Amber.local> 1785344041 -0700
```

`xian@Amber.local` is an unroutable local hostname address. Any publish commit I made would land on
website `origin/main` mis-attributed, with no error and nothing to catch it — the commit succeeds.
The **product** repo is correctly configured (`mediajunkie` /
`3227378+mediajunkie@users.noreply.github.com`), which is why this is invisible unless you check the
second repo specifically.

This is a variant of onboarding-delta trap **#8** (provisioner git identity leaking). The catalog
describes a *wrong* identity leaking in; this is *no* identity at all, so git silently invents one.
Same class, opposite mechanism, same silent-failure signature — and it is exactly the case that
"confirm both worktrees before your first publish" was pointed at. **Not yet fixed — proposing
rather than acting, since git identity on PM's repo is PM's call.**
