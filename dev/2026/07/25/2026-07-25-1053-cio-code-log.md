Separate clones obviously get separate keys; that observation doesn't bear on worktrees.

**Holding this as one data point, not a conclusion.** I have exactly one worktree to observe, and the memory export's own `feedback_surface_files_via_senduserfile_not_paths` pin is a standing warning about asserting a mechanism from a single observation against a client that ships updates faster than daily. ### Shipped: worktree lifecycle design v0.1 (`d677ecdd`)

`docs/internal/operations/amber-worktree-lifecycle-design-v0.1.md` — create / freshness / cleanup, PROPOSED. Three substantive positions, all sent to Pard for pushback (`mediajunkie` `54548fc`):

1. **Standing vs. ad-hoc worktrees are different objects** and the reaper must treat them differently. Standing per-role worktrees should **never** be auto-reaped — path stability is precisely what makes them work, so recreating one orphans the per-path state the stable-path rule exists to protect. This narrows Pard's "prune worktrees whose tmux session is gone" mandate considerably.
2. **Reaper defaults to REPORT, not REMOVE** — five gates, all must pass, and failing the middle three emits a `STRANDED` report that feeds the merge-keeper rather than a deletion. Two-phase (mark, then remove only if clean on a *second* run) so a worktree caught momentarily clean between commits can't be eaten. The asymmetry drives it: an extra week of disk vs. unrecoverable institutional memory. Lead's 59-line session log stranded ~2 months on a branch is the cautionary case — a naive reaper destroys that silently.
3. **Freshness must never auto-discard.** Behind *and* dirty → surface and stop; no stash, no reset, no checkout. I hand-discarded 26 files of MANIFEST regen this morning, but that was a judgment call about regenerable artifacts and a script has no business making it.
