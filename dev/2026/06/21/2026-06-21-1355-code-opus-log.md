## Investigation / determination

**Test-fixture-induced, NOT a normal prod crash — but masking genuine latent fragility.**

- Prod reads `created_at`/`updated_at` from PostgreSQL `TIMESTAMP WITH TIME ZONE`
  (`StandupConversationDB` via `TimestampMixin`, `DateTime(timezone=True)`) → tz-aware
  → the three subtractions work in prod.
- Failures come from the test doubles NOT reproducing Postgres tz-awareness:
  - 8 manager tests use **in-memory SQLite** (`test_conversation_state.py` `manager`
    fixture) → SQLite drops tzinfo on round-trip → `repo.get_by_id` returns **naive**
    `created_at`; `completed_at` is set tz-aware in Python (`datetime.now(timezone.utc)`)
    → `completed_at - created_at` crashes (:339); same for `now - created_at` (:355).
  - 1 adapter test uses the **in-memory Fake** whose `transition_state` set
    `updated_at = datetime.now()` (naive) → `now(utc) - updated_at` crashes (:302).
- Root cause worth fixing regardless: the domain model `StandupConversation`
  (`models.py:2216-2217`) AND `StandupConversationRepository.update`
  (`repositories.py:2643`) both emit **naive** `datetime.now()`. Prod safety is
  *incidental* to Postgres normalization; also a latent prod correctness nuance
  (naive-LOCAL written to timestamptz is interpreted per session tz).

## Fix (defense-in-depth, layer-correct) — IN PROGRESS
