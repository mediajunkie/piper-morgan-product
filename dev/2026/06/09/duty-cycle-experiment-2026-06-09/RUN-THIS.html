Duty Cycle Experiment: Local vs Cloud Session Surfaces

Filed 2026-06-09 · CIO · run time ≈ 24h after launch
What we're testing: Whether a Code session started from Desktop with cloud selected behaves differently from one started with local + worktree, on dimensions that matter for autonomous duty cycles: cron firing, overnight survival, file/git access, output rendering.

What you'll do: Launch 2 new Code sessions, paste a kickoff prompt into each, confirm both report back, then leave them alone for ~24h. Come back tomorrow afternoon and we read the results.

What stays constant across both: model (Sonnet 4.6), effort (default), cron offset (:33), prompt template (only the agent slug differs), test window (~24h).

Total active time on your part: ~10 minutes now + ~5 minutes tomorrow.

Before you start

  • Have Claude Desktop open and ready.
  • Confirm the experiment directory exists: /Users/xian/Development/piper-morgan/piper-morgan-product-cio-cycle/dev/active/duty-cycle-experiment-2026-06-09/ (created — this HTML file lives there).
  • Pick a moment when you can spend ~10 uninterrupted minutes on launch.
  • Choose your model setting in both sessions: Sonnet 4.6 (we want a real-world data point on the model we're piloting; also keeps cost low while the test runs).

Part 3 — Leave it alone for ~24h

11Close the Desktop UI if you want; let the sessions run in background. The whole point is to see how each surface handles being left alone (and how it handles your laptop sleeping, if it does overnight).
12Don't intervene unless something goes obviously wrong. Each session should fire hourly at :33, append a row, and idle. If neither session writes any new rows after the first hour, that itself is data — but generally hands-off.

Part 4 — Check-in ~24h later

13Open the two log files in your editor or a terminal:
  • dev/active/duty-cycle-experiment-2026-06-09/test-local-log.tsv
  • dev/active/duty-cycle-experiment-2026-06-09/test-cloud-log.tsv
14Bring me what you see and we'll compare. The high-leverage questions:
  • Fire counts — did each session fire ~24 times, or did one die early?
  • Timing — were fires actually at :33, or did they drift?
  • Overnight — did either session survive a sleep/lid-close?
  • Git — did commits from both reach origin/main? If you ran git log --oneline origin/main | grep test-, do you see entries from both?
  • The free-text observations column — anything either session noticed that surprises us.
15Decide. Based on what we see, we either: (a) lean into cloud for the rest of the migration, (b) stay on local + worktree (incumbent) with confidence, (c) discover something that changes the question entirely. All three are legitimate outcomes.

If you hit something weird at launch

  • Session won't register a cron / says "CronCreate not available" — let it document this and try whatever scheduling it does have (Routines, slash command, whatever). Surface differences are exactly what we want to learn.
  • Session lands in a weird cwd — let it report the cwd verbatim. Don't try to cd it into the canonical path; we want to see what the surface gives you by default.
  • Git push fails from one session but not the other — that's a major data point. Let it document the failure mode rather than fix it.
  • Session asks "are you sure?" about anything destructive — say no, this is a read-mostly test, no destructive ops needed.
  • Anything else surprising — note it and we'll discuss tomorrow.
