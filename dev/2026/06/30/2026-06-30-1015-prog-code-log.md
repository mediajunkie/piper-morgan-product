## Task
`SlackConfigService.get_config(user_id)` REQUIRES user_id (ADR-058). `SlackClient` calls
`get_config()` with no user_id at 3 sites (_ensure_session, _check_rate_limit, _make_request)
and __init__ stores no user_id → latent TypeError. Thread user_id through.

## Investigation findings (Verify First)
The bug is REAL and confirmed. But the blast radius is LARGER than the prompt's caller map:
`SlackClient` is built EAGERLY inside `SlackIntegrationRouter.__init__` (router.py:70, :84), and
the **router is a startup SINGLETON** — confirmed by `slack_plugin.py:69-75` comment (#784):
"At plugin startup, there's no user context available." The router is constructed in MANY
singleton/background contexts:
- `slack_plugin.py:30` (module-import singleton)
- `reminder_scheduler.py:64` (background scheduler)
- `webhook_router.py:63` (per-app singleton); **CRITICAL: webhook_router:82 passes the ROUTER
  itself as `slack_client` to SlackResponseHandler** → in prod the response_handler's
  `self.slack_client` IS the router, not a raw SlackClient.
- `response_flow_integration.py:188` (per-operation, `async with`)
- `context_assembler.py:1666` (per-operation, has user_id as method param)
- `settings_integrations.py:2076` (`SlackIntegrationRouter()` — no config_service)

### Decision: EAGER vs LAZY → LAZY per-operation client construction
user_id is per-REQUEST/per-operation everywhere; router is a singleton. Threading user_id into
router.__init__ is WRONG (doesn't fit usage). Instead: router builds/uses the SlackClient per
operation with that op's user_id. The router's operation methods (send_message, list_channels,
etc.) gain a `user_id` param threaded down to SlackClient → get_config(user_id).

### Per-caller user_id source
- webhook_router → `_get_connector_user_id()` = `SLACK_CONNECTOR_USER_ID` env (the connector
  owner; #759 alpha multi-tenancy pattern)
- standup_reminder_job._send_reminder → per-reminder `user_id` (in scope at call)
- context_assembler._fetch_slack_activity_items → `user_id` method param
- response_flow_integration → `ResponseTarget.user_id` field
- settings_integrations.get_slack_channels → `current_user.sub`

### Guardrail / flagged gaps
- `SlackClient.__init__` → make `user_id` REQUIRED.
- A SlackClient that can't call get_config is useless; never pass None.

## CRITICAL FINDING — two user_id namespaces (10:50)
In the webhook→response path, `slack_context["user_id"]` = `event.get("user")` = the SENDER's
Slack workspace user ID (e.g. U07...), NOT the Piper user_id used for keychain credential
lookup. `SlackConfigService.get_config(user_id)` keys the bot-token keychain entry by the
CONNECTOR-OWNER's Piper user_id (`SLACK_CONNECTOR_USER_ID`, #759; future #760 maps via
slack_workspaces by team_id). So threading slack_context["user_id"] into get_config would look
up creds under the WRONG key.

Fix: webhook context build now also carries `connector_user_id` (= _get_connector_user_id()).
Response handlers send with `user_id = slack_context.get("connector_user_id") or
slack_context.get("user_id")` — connector-owner creds for the outbound bot send. If neither is
present → genuinely user-less; flagged.
