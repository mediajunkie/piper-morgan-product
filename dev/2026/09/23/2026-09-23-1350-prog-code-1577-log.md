## Investigation

  `if timeframe == "today"/"yesterday"/"last_week"/"last_month"` elif chains in
  `find_decisions` (line ~231) and `get_relevant_context` (line ~342).
- Read `services/intent_service/temporal_utils.py` in full. `parse_relative_date(message,
  user_timezone=None)` is the single canonical calendar-day resolver (#1572: takes an
  optional IANA tz via `_anchor_now`; without one, falls back to the pre-#1572 server-local
  aware anchor — fail-safe, unchanged). It supports "tomorrow"/"next week"/"this
  week"/default-"today" but has **no "yesterday" branch at all**.
- Per the dispatcher's explicit constraint ("touch temporal_utils ONLY if consuming an
  existing function, never widening it"), I did **not** add a "yesterday" keyword to
  `parse_relative_date`. Instead: `document_service` now calls
  `parse_relative_date("today", user_timezone)` to get temporal_utils' canonical
  `today_start`, then derives `yesterday = today_start - timedelta(days=1)` **locally** —
  the exact mirror of how `parse_relative_date`'s own "tomorrow" branch derives
  `today_start + timedelta(days=1)`. This consumes the existing function without adding
  any new vocabulary to it.
- Confirmed `owner_id` (both call sites' principal param) is `Union[str, UUID, None]` —
  the same shape `UserPreferenceManager.get_reminder_timezone(user_id)` already coerces
  via `_as_uuid`/`_ckey`, so it can be passed straight through with no explicit cast.
- Confirmed #1574 (JSONB user-scope persistence, just landed) makes
  `UserPreferenceManager().get_reminder_timezone(owner_id)` a real DB-backed read (not the
  pre-#1574 always-default facade F6 described) — safe to call fresh per-request.
- Found the exact precedent for the fail-safe wrapper shape in
  `services/mcp/consumer/google_calendar_adapter.py:479-483` (`get_user_timezone`):
  `UserPreferenceManager().get_reminder_timezone(...)` in a local import, wrapped in
  try/except, logged-and-defaulted on failure. Mirrored that shape.

## Implementation

`services/knowledge_graph/document_service.py`:
- Added `from services.intent_service.temporal_utils import parse_relative_date` (top-level
  import; verified no circular-import issue — `python -c "import
  services.knowledge_graph.document_service"` succeeds).
- Added `_calendar_today_start(self, owner_id) -> datetime`: resolves the owner's stored tz
  preference (local import of `UserPreferenceManager`, fail-safe try/except, `#
  silent-ok:`-annotated per the silent-death ratchet), then returns
  `parse_relative_date("today", user_timezone)[0]` — the single "today" boundary both
  functions now share.
- `find_decisions`: `"today"` → `await self._calendar_today_start(owner_id)`; `"yesterday"`
  → that minus one day. `last_week`/`last_month`/else unchanged (no temporal_utils
  counterpart, no audit finding against them — left alone to keep blast radius minimal).
- `get_relevant_context`: same for `"today"`; the `else` branch (its default, and any
  unrecognized timeframe string) now means "yesterday" via the same calendar boundary
  instead of `now - timedelta(days=1)`. `last_week`/`last_month` unchanged.
- Net effect: the two functions' "yesterday" (explicit or defaulted) now resolve to the
  IDENTICAL instant — closing the "same query, different answer by entry path" bug — and
  that instant is a true calendar-day boundary, not a rolling window.

### User tz threading

**Threaded.** `_calendar_today_start` looks up `owner_id`'s stored timezone via
`UserPreferenceManager().get_reminder_timezone(owner_id)` (the #1574 DB-backed getter) and
passes it into `parse_relative_date(..., user_timezone=...)`. When `owner_id` is `None` (or
the lookup raises), it silently degrades to `parse_relative_date`'s server-anchor fallback —
never crashes a document query over a missing/bad tz.
