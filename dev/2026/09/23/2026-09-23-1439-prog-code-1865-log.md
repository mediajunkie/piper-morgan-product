## Task

`scripts/surface1_counterfactual_probe_1283.py` monkeypatches `PreClassifier.pre_classify`,
but `services/intent_service/classifier.py:419` calls
`PreClassifier.pre_classify_with_pattern_list(...)` directly, so the patch never takes
effect and the probe's bypass-verification assertion (`bypass not consulted`) fires on the
first corpus row, every run.

## Investigation

- `services/intent_service/classifier.py:419` (inside `IntentClassifier.classify()`, the
  method the probe's `run()` calls): `pre_intent, preclaim_pattern_list =
  PreClassifier.pre_classify_with_pattern_list(message)` — this is the ONLY Stage-1 call
  site inside `classify()`. `classify()` never calls `pre_classify` directly (confirmed via
  grep across `classifier.py`; the only other `PreClassifier.*` call in that file is
  `detect_multiple_intents` at line 703, inside the separate `classify_multiple()` method,
  which the probe does not exercise).
- `services/intent_service/pre_classifier.py:1173-1184`: `pre_classify` is a **thin
  delegator** over `pre_classify_with_pattern_list` — `intent, _pattern_list =
  PreClassifier.pre_classify_with_pattern_list(message); return intent`. So direction is:
  `pre_classify` → delegates to → `pre_classify_with_pattern_list` (never the reverse).
- Conclusion: `pre_classify_with_pattern_list` is the one live entry point `classify()`
  consults. Patching `pre_classify` (as the script did) leaves the real gate untouched — the
  monkeypatch is a no-op from `classify()`'s point of view, so `pre_classify_with_pattern_list`
  still answers for every corpus row, `bypass_calls["n"]` never increments, and the
  `assert bypass_calls["n"] == expected_consultations` fires on row 1. Exactly matches the
  issue's diagnosis.
