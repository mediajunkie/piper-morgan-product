So: (a) the classifier extracts **no slots** — there is nothing already-extracted in `intent.context`

same pattern as turn 1**, because it contains the literal token "new project".

### The handler seam

`services/intent_service/canonical_handlers.py::_handle_portfolio_query` sniffs an operation from
the message, then `operation == "add"` (line ~4245) ignores `original_message` entirely and emits a
fixed prompt, after creating a `PortfolioOnboardingManager` session in `GATHERING_PROJECTS`.

### 🔴 The load-bearing finding: the multi-turn add flow is a DEAD END in production

`services/process/adapters.py:609` —
```python
    # ADR-059: Onboarding disabled — put on ice until workflow dispatcher is in place
    # registry.register(OnboardingProcessAdapter())
    registry.register(StandupProcessAdapter())
```
The onboarding adapter is **commented out**. And `IntentService._check_active_onboarding` (the legacy
direct route) **has no production caller** — `grep` finds it only in its own `def` and in tests.

Therefore no follow-up turn can ever reach `PortfolioOnboardingHandler.handle_turn`. The session the
add branch creates is an orphan, and its question ("What would you like to call it?") is **an open
question the system is structurally incapable of hearing the answer to.**

Corroborating probes (all run in-process this session, env-stripped):
- `check_escape(turn2, ONBOARDING)` → `None` (not an escape)
- `detect_off_topic(turn2, ONBOARDING)` → `is_off_topic=False`
- `registry._is_escape_command('cancel')` → `True` (which is why 'cancel' worked for PM)

**So defect 2's mechanism is not "the state machine failed to detect a repeat" — it is that there is
no state machine on the path at all.** Turn 2 re-enters the add branch from scratch and re-emits the
canned line verbatim. Any fix that only hardens `_handle_gathering` in
`services/onboarding/portfolio_handler.py` would be unreachable code.
