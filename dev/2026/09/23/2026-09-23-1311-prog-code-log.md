## Design decisions / deviations worth flagging to PA

- **Deviation (per explicit instruction)**: `usage-capture.sh` does not commit or push. The append
  logic is complete and tested; the commit/push block exists only as a commented-out TODO sketch
  for PA's review.
- **Comment-block placement**: I created the TSV with header only, ran the writer live to capture
  the two real rows, then hand-appended the account→seats comment block at the true bottom
  afterward (matching the spec's "bottom of the same file" framing for this one-time block). The
  writer itself does a plain file append — it does not reorder or re-splice the comment block on
  later runs, so once this build's crontab is eventually installed, future automated rows will
  land *after* this comment block rather than before it. Functionally this is fine (readers skip
  `#` lines regardless of position; `usage-lookup.sh` does), and I documented this explicitly in a
  trailing note inside the comment block itself so a future reader isn't surprised by it. I chose
  not to build reorder/re-splice logic (read whole file, split trailing comment, re-append after
  new rows) because it adds real complexity for a purely cosmetic property the spec doesn't
  actually require (spec's only hard requirement is "readers must skip `#` lines," which is met).
  Flagging this as a judgment call, not a silent shortcut — happy to add the splice logic if PA
  wants the block to stay literally last.
- **`config_dir` column**: I write the literal strings `~/.claude-pm` / `~/.claude` (matching the
  spec's example row) into that column, not the reader's own echoed field 1 (which comes back as
  the tilde-expanded absolute path, e.g. `/Users/xian/.claude-pm`, since the reader expands `~`
  internally before echoing). The account label column already disambiguates; using the literal
  form keeps the TSV matching the spec's worked example exactly.
- **`source` column**: set to `$(basename "$READER")`, so it reads `usage-read.sh` for the real
  reader (matches spec) and the stub's own basename in tests — same mechanism, no special-casing.
- Numeric validation on the "good line" path (`^[0-9]+(\.[0-9]+)?$` on both percentage fields)
  before accepting it as real data — a defensive belt-and-suspenders on top of the field-count
  check, so a 5-field line with corrupted-but-tab-shaped content still can't masquerade as a good
  reading.
- No changes made outside the five files listed in the spec's AC (D1 TSV, D2/D4/D5 scripts, this
  log). Nothing discovered outside scope during this build — no separate issue filed.
