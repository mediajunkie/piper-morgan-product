Shared helper `_assert_authenticated_users_do_not_leak_turns(intent_service, category)`: fresh
`session_id` + two distinct `uuid4()` user_ids sharing that ONE session_id, calls
`process_intent(message, session_id=session_id, user_id=...)` for both (via a tolerant wrapper
that swallows only the expected #1831 no-LLM-provider failure for the 7 Stage-2 categories), then
asserts:
- `ctx_a is not ctx_b` (distinct user_ids must not resolve to the same context object)
- `len(ctx_a.turns) == 1 and ctx_a.turns[0].message == message` (no cross-user leakage)
- `len(ctx_b.turns) == 1 and ctx_b.turns[0].message == message`

These are exactly the assertions that would fail if the composite key ever collapsed to
session-only (the #1394 defect class: a handler drops `user_id` and both principals share the
`anonymous:{session_id}` — or any coinciding — context).

Module docstring updated with: the audit citation, the classification rationale, and the standing
review rule verbatim from the audit's TEST-BLIND section ("any new test of a
`{user_id or 'anonymous'}:{session_id}`-keyed surface must assert at least once under a non-None
user_id — a probe where the keys coincide is a config check, not a verification (m-44)").
