## Fix (resolver-side, `services/database/repositories.py`)

Added `normalize_project_name(name: str) -> str` (module-level, near `ProjectRepository`):
```python
_LEADING_ARTICLE_RE = re.compile(r"^(?:the|my)\s+")
_TRAILING_NOUN_RE = re.compile(r"\s+(?:project|repo)$")
_WHITESPACE_RE = re.compile(r"\s+")

def normalize_project_name(name: str) -> str:
    normalized = _WHITESPACE_RE.sub(" ", name.strip()).lower()
    normalized = _LEADING_ARTICLE_RE.sub("", normalized)
    normalized = _TRAILING_NOUN_RE.sub("", normalized)
    return normalized.strip()
```
and `_resolve_unambiguous_normalized_match(query_name, candidates) -> Optional[ProjectDB]`:
exact-normalized match first (both sides normalized); returns `None` (never guesses) if
zero or >1 candidates match; only then a single-candidate substring/prefix fallback on
normalized forms, itself only used if unambiguous.

`ProjectRepository.find_by_name` keeps its existing fast-path exact case-insensitive SQL
query unchanged; **only on a miss** does it fetch the same owner/archived-scoped candidate
set (second query) and resolve via `_resolve_unambiguous_normalized_match`. Not a
`TestExtractionPatternRatchet`-tracked surface (that ratchet only scans specific named
spans in `todo_handlers.py` / `drafted_issue.py` / `intent_service.py` /
`pre_classifier.py` — verified by running the ratchet, see below).

`PortfolioService.find_project_by_name` docstring updated to note the delegate's new
tolerance (no code change — it already just forwards to `find_by_name`).
