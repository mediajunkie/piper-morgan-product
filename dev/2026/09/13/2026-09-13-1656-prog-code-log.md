### 2. The deeper defect — the SERVER accepts a client-supplied principal

`web/api/routes/personality.py` took the principal from the client on all three routes:
- `GET /profile/{user_id}` — path param, no auth dependency at all
- `PUT /profile/{user_id}` — path param; `Depends(require_admin)` (the #1734 gate)
- `POST /enhance` — `data.get("user_id", "default")` from the request body

That is the multi-tenancy shape #1751 names: the client names the principal on a write path.

### 3. The store is GLOBAL — there is no per-user personality data today

`web/personality_integration.py:50-75`: `PiperConfigParser.load_personality_config(user_id)` and
`save_personality_config(config, user_id)` **both ignore `user_id` entirely**. Both operate on a
single instance-wide file, `config/PIPER.user.md` (ADR-075 D4 overlay). So the endpoint is
genuinely instance-wide config, not per-user preferences. `users.preferences` (JSONB,
`services/database/models.py:161`, #1422) exists and is the natural future home, but moving the
store there forks it from the ADR-075 overlay that `user_context_service` reads — architecture
work, not this issue. Filed as discovered work.

### 4. Admin-gate claim — verified behaviorally, and it was only HALF true

Pre-fix probe, real app / real `AuthMiddleware` / real JWT / real file on disk
(`scratchpad/probe_gate.py`, throwaway):

```
unauth   PUT /profile/default   → 401
non-admin PUT /profile/default  → 403   overlay unchanged: True
ADMIN(A)  PUT /profile/<user B> → 200   overlay rewritten by that PUT: True
```

So the issue body's claim ("the PUT is admin-gated, blast radius limited") is **correct for
non-admins and incomplete for admins**. An admin could aim the write at an arbitrary other
principal's id and get a 200 plus a global overlay rewrite. #1734's gate bounded *who* could
write; it never closed the cross-user-write *shape* the issue worried would "return if the gate
is ever relaxed" — for admins that shape was live the whole time. Severity is still bounded by
who is an admin, but the assessment "the shape is held back by the gate" was not accurate.

Second finding, same probe: the **GET had no auth dependency at all**. It was protected only by
`AuthMiddleware` (the path is not in `DEFAULT_EXCLUDE_PATHS`) — one exempt-list edit away from
being an anonymous read of any named principal.

## Fire 1 — #1751 fix

**Fix shape**: remove the client-supplied principal rather than validate it. Both inputs deleted:
the `{user_id}` path segment on GET/PUT, and `/enhance`'s `data.get("user_id", "default")`.
Principal now from `Depends(get_current_user)` (GET, /enhance) and `Depends(require_admin)` (PUT,
#1734's gate preserved). Responses carry a literal `"scope": "instance"` so the payload cannot be
misread as per-user data (it isn't — see below).

Took the issue's own second AC branch ("the page honestly presents itself as instance-wide …
until scoping exists") because the store genuinely IS instance-wide. Did NOT rewrite the store:
that forks `config/PIPER.user.md` from `user_context_service`, which is an Arch decision, not a
bug fix. Filed as #1791.

1792 was found by accident while writing the real-app tests: five sequential authenticated GETs
with freshly-minted valid tokens give `200, 401, 401, 401, 401`, the 401s reading "Token has been
revoked". A fresh `jti` cannot be blacklisted, so that is the fail-closed branch of
`is_blacklisted` mis-reporting *unavailable* as *revoked* — the opposite of the 503
"couldn't verify right now" idiom `require_admin` uses for the identical situation. Redis was up
(`:6379`); the trigger in-harness is loop-per-request connection reuse, but the production trigger
is any Redis blip. Practical consequence for test authors until it's fixed: **a bare `TestClient`
gets one authenticated request.**
