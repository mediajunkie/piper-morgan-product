## Design section (written BEFORE coding, per the dispatch)

**Verdict: STOP. Option (a) as specified is not buildable, and the reason is not a missing
segment — it is that the consult's output and the orchestrator's input are disjoint sets.**

1. **Where the segments would come from.** `detect_multiple_intents` discards its match objects:
   `_matches_patterns` does `re.search(...)` and returns a bool. The span is recoverable with no
   second pass and no new regex literal — add `_first_pattern_match(msg, patterns) -> Optional[Match]`
   and make `_matches_patterns` a byte-identical delegator (`is not None`), then record
   `match.span()` per appended Intent in a `claimed_span_by_id` dict keyed by object identity
   (realigns across `_apply_subsumption_filter` for free, exactly as `pattern_lists` does since the
   pre-claim probe) and surface it as a new `MultiIntentResult.spans` field. #1755 already retains
   `connect_match.span()` for the temporal skip, so this is the same idiom widened.
   `TestExtractionPatternRatchet` is untouched (no literal added). **Segments** = sort anchors by
   span start; sibling *i*'s segment runs from its own anchor start to the NEXT anchor's start
   (segment 0 extended back to index 0), mapped back to the ORIGINAL (un-lowercased) message by the
   leading-whitespace offset, guarded by `len(stripped.lower()) == len(stripped)`. This keeps each
   half's arguments with its own verb. **So the segmentation half is feasible.** It is not what
   fails.

2. **Where the per-sibling consult would run.** Not at the existing seam: the seam sits before
   `classify_multiple`, and pre-empting it would bypass Stage-0 B3, the classifier cache and the
   pre-claim probe. It would run immediately AFTER `classify_multiple` returns and BEFORE
   `_substantive_intents` is computed, gated on `multi_result.spans` being populated (only the
   surface-1 detect path fills it — B3 and the LLM fallback construct `MultiIntentResult` without
   spans, so they are structurally excluded). The whole-message consult at the existing seam would
   stand down on a split turn, gated by a cheap deterministic `detect_multiple_intents` probe that
   runs only when the flag set is non-empty (default-empty ⇒ zero extra work, byte-identical).

3. **What happens on `None`.** The sibling keeps its surface-1 Intent, byte-identical to today;
   replacement is in place at the same list index, so `pattern_lists`/`spans` alignment survives and
   `primary_intent`/`has_greeting`/`is_multi_intent` are unchanged.

4. **Why the orchestrator's all-canonical check does NOT cover the result — the blocker.**
   Arch's Q2 ruling verified that `_is_orchestratable_sibling` "operates on the resulting Intent
   object, not on which router produced it." That is true, and it is the refusal layer only (m-43).
   What it does not say is *which way the predicate answers* for a consult-produced Intent. The
   orchestrator does not dispatch on `intent.action` at all: `_execute_single` gates on
   `CanonicalHandlers.can_handle`, which is pure category membership in
   `{TEMPORAL, GUIDANCE, PORTFOLIO, CONVERSATION, PROVENANCE}`, and `handle()` then branches on
   `intent.category`. **There is no #1124 action rail on the multi-intent path.** The consult, by
   construction, emits `IntentCategory.QUERY` for any rail op with no ACTION_REGISTRY category and
   the registry category otherwise. Measured over the live rail: **0 of 127 rail keys produce a
   consult category the orchestrator can execute** (123 QUERY, 3 EXECUTION, 1 SYNTHESIS; none in
   the canonical five). Conversely the two categories the #1755 shape actually yields — TEMPORAL
   (`get_current_time`) and GUIDANCE (`get_contextual_guidance`) — **are not rail keys at all**, so
   their consults can never return an Intent (`entry is None` ⇒ `not_rail_dispatchable`).
   The consult's output set and the orchestrator's input set do not intersect.

   Consequence: a replacement cannot improve an orchestrated turn; it can only convert an
   all-canonical plan into one with a non-orchestratable sibling, which fires the #1763 branch and
   sends the whole turn to the floor. **The safety net does not cover the result — it rejects every
   possible result.** And the #1190 destructive confirm lives in the surface-3 rail dispatch inside
   `process_intent`, not in the orchestrator, so a `delete_todo` sibling would never reach
   `build_todo_delete_confirmation` on this path (safe — nothing deletes — but the specified test-2
   behavior is unreachable).

5. **#1606 specifically — surface 1 never splits it.** Measured this turn on the corpus verbatim:
   `detect_multiple_intents` returns **zero** intents; `pre_classify` claims the whole thing as
   `query/set_default_repo`. Lead's question memo assumed "today #1606's turn arrives as two
   pre-classifier intents"; that premise is false, and the issue's own last comment says the same
   ("still claimed whole by query/set_default_repo @1.0 at surface 1"). Option (a) keeps the split
   at surface 1, and for #1606 there is no split to keep. Manufacturing one needs a clause/
   conjunction segmentation regex — a new extraction pattern, which the dispatch forbids and
   `TestExtractionPatternRatchet` would fail. Routing both halves therefore requires the router to
   return an ordered plan: **option (b)**.

6. **Two further specified tests are unreachable independent of the above**: test 2 needs
   `set_default_repo` to flip, but it is WRITE and not on `FLIP_WRITE_ALLOWLIST`
   (`{delete_todo, create_reminder, create_todo}` as of this turn — `delete_todo` added by the
   concurrent unit-3b lane); test 6 needs `get_current_time` consult-routable, but it is not a rail
   key.
