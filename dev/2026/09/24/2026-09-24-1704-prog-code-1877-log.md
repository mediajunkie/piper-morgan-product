## Investigation

Built a throwaway probe (`/private/tmp/.../scratchpad/probe_dispositions.py`, not shipped) that
mirrors `process_intent`'s real dispatch order for every `(category, action)` registry row:
1. `IntentService._should_route_to_floor(intent)` → FLOOR
2. else `CanonicalHandlers.can_handle(intent)` → CANONICAL
3. else `normalize_action(action) in get_action_workflows()` (#1124 rail) → WORKFLOW
4. else the category's own post-rail terminal path (traced by reading
   `_handle_query_intent`/`_handle_analysis_intent`/`_handle_execution_intent` source directly)

First pass (registry unchanged, rail unregistered — forgot `register_default_workflows()`)
showed 46 apparent mismatches, almost all false positives from an incomplete runtime model.
After calling `register_default_workflows()` (idempotent; the #1124 rail's `WORKFLOW_REGISTRY`
dict is empty until something calls it) the true count dropped to 12, then after tracing the
remaining fallback paths (QUERY/ANALYSIS unconditionally floor past the rail via
`_handle_generic_query`/`_handle_unknown_intent`; three EXECUTION actions still dispatch via a
pre-#1124 elif chain in `_handle_execution_intent` at intent_service.py:9573/9598/9622) down to
the **6 genuine mismatches**:

**Canonical-but-gated-off finding (reported, not silently flipped or hidden)**: STATUS and
PRIORITY still have live handler methods — `CanonicalHandlers._handle_status_query`,
`._handle_priority_query`, `._handle_status_report` (canonical_handlers.py:694, 1105, 3317) — but
they're unreachable from the chat `IntentService` gate (STATUS/PRIORITY absent from
`can_handle()`'s `canonical_categories` set). They are NOT dead code: they're live-called from
`services/integrations/slack/webhook_router.py` and referenced in
`services/commands/definitions.py` — the Slack/slash-command surface, a different entry point
than the chat `process_intent` path this registry describes. So the FLOOR flip is correct for
chat; the ACTION_DESCRIPTIONS citation comments for these two rows were updated to stop
implying the chat-canonical handler is live. No test carve-out was needed since FLOOR is the
unambiguous correct disposition for the chat surface in both cases — this is a discovered-work
note, not a disposition disagreement.

GUIDANCE/get_contextual_guidance and TEMPORAL/get_current_time and CONVERSATION/greeting are
genuinely message-dependent (conditionally canonical) — confirmed correct already, using a
setup-request message override for GUIDANCE (its plain `ACTION_EXAMPLES` phrasing is
deliberately a non-setup floor case) to prove the CANONICAL branch is reachable, same
methodology #1773 used for greeting's pleasantry-only carve-out.
