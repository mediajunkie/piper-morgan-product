## Step 1 — span representation, BEFORE

- `_integration_connect_match(clean_message)` already returns a real
  `re.Match` object (not just a bool) — it carries `.span()` for free. BUT
  the loop that consumes it (`detect_multiple_intents`) only read
  `connect_match.group("integration")` for `setup_target` and threw the
  match away; no span was retained past the `if patterns is
  INTEGRATION_CONNECT_PATTERNS:` block (local var scoped to that iteration
  only in intent, not in enforced scope, but nothing downstream read
  `.span()`).
- The TEMPORAL side had NO match object at all — `_matches_patterns()`
  (the function that gates the TEMPORAL group's append) returns a plain
  `bool` (`re.search(pattern, message)` inside a loop, span discarded).
  The blanket skip (`if patterns is TEMPORAL_PATTERNS and connect_claimed:
  continue`) never even got as far as attempting a temporal match — it
  short-circuited the WHOLE group before `_matches_patterns` ran.
- So: connect's span was available but unretained; temporal's span was
  never computed at all on this path. Both needed plumbing, no new pattern
  literal required (reusing `TEMPORAL_PATTERNS` and
  `INTEGRATION_CONNECT_PATTERNS` as-is).

## Step 2 — the fix

`services/intent_service/pre_classifier.py`:
- Hoisted `connect_span: Optional[Tuple[int, int]] = None` above the loop;
  set it (`connect_match.span()`) alongside `connect_claimed = True` when
  the connect group claims.
- Added `PreClassifier._temporal_disjoint_from_connect(clean_message,
  connect_span) -> bool`: iterates every `TEMPORAL_PATTERNS` entry with
  `re.finditer` (not `re.search`, so a pattern that matches once inside the
  connect span and again outside it isn't shadowed by its own first hit),
  returns True on the first match whose span is disjoint
  (`m_end <= c_start or m_start >= c_end`).
- Replaced the blanket skip:
  ```python
  if (
      patterns is PreClassifier.TEMPORAL_PATTERNS
      and connect_claimed
      and connect_span is not None
      and not PreClassifier._temporal_disjoint_from_connect(
          clean_for_matching, connect_span
      )
  ):
      continue
  ```
  i.e. skip (suppress) TEMPORAL only when no disjoint temporal match
  exists; otherwise fall through to the existing
  `_matches_patterns(...)` + append logic unchanged (it re-matches and
  will find the same pattern that proved disjointness — no double work
  beyond one extra `finditer` pass, and no behavior change to *how* the
  intent is constructed).
- Ratchet safety: `_temporal_disjoint_from_connect` calls
  `re.finditer(pattern, clean_message)` where `pattern` is a bare loop
  variable (`ast.Name`), not an inline literal — `_count_regex_literals`
  in the ratchet only counts inline (non-Name) regex-call arguments, and
  separately `_pre_classifier_count()` only sums `*PATTERNS` list lengths
  at `PreClassifier`'s class-body top level. No new list, no new element,
  no new inline `re.*` call — the count is mechanically unchanged (verified
  by running the ratchet test before/after, see gates below).

## Step 3 — ordering finding (for the report)

Pattern-group order in `pattern_groups` is FIXED PRIORITY, not
message-position-based: `INTEGRATION_CONNECT_PATTERNS` (index ~16) is
checked and appended before `TEMPORAL_PATTERNS` (index ~17) regardless of
where each phrase sits in the actual message. So
`'what time is it? also connect my github'` — where the temporal words
come FIRST in the text — resolves as
`[(GUIDANCE, get_contextual_guidance, 'github'), (TEMPORAL,
get_current_time)]`, i.e. **connect first, temporal second** — neither
"temporal first" nor strict message order. This matches the pre-existing
#1505 ordering convention (e.g. greeting-before-connect is also priority-
order, not message-order — see `test_greeting_plus_connect_keeps_both_parts_1505`).
The new test pins this actual order and documents why (priority-list
iteration, not message position) rather than asserting an order the code
doesn't produce.
