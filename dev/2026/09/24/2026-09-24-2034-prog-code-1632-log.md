## Diagnosis

1. **Routing probe**: `what can you do?` → pre-classifier `DISCOVERY_PATTERNS` claims
   it deterministically as `DISCOVERY`/`get_capabilities` (surface 1,
   `services/intent_service/pre_classifier.py`). `action_registry.py` disposition:
   `("DISCOVERY", "get_capabilities"): ActionDisposition.FLOOR` (#1877 — no
   DISCOVERY branch in `_requires_canonical_handler`, falls to the floor).
   Confirmed: the turn is floor-routed, not action-railed.

2. **What the floor receives**: `ContextAssembler.gather_context("DISCOVERY")` →
   `_gather_identity_context` → `context["capabilities"] = capability_answer_lines()`
   (from `chat_pointers.py`, the **#1428** ledger — a completely SEPARATE derivation
   from `capability_legibility.capability_catalog()` (the #1462/#1509/#1632 module).
   `capability_legibility.py`'s own module docstring states this explicitly: *"The
   'what can you do?' answer path already derives from the same ledger
   (chat_pointers.capability_answer_lines, #1428) — untouched; this module adds the
   effect/consent dimension without forking that surface."* The #1632 build closed
   the catalog-derivation half but never touched the #1428 consumer that actually
   renders into the DISCOVERY prompt. **Confirmed root cause: plumbing gap (a)** —
   the marker never reached the prompt because the two catalogs were never wired
   together.

3. **Second, deeper finding** (verified live, not assumed): the #1428 `CHAT_POINTERS`
   ledger has **zero POINTER rows** targeting any of the 9 OUTWARD rail keys
   (`comment_issue`/`add_comment`/`comment_issue_query`/`create_issue`/
   `create_github_issue`/`create_item`/`create_ticket`/`make_github_issue`/
   `new_github_issue` — the comment/create-issue family, confirmed via
   `WORKFLOW_REGISTRY` + `Outwardness.OUTWARD` filter). So even a correct fix to the
   #1428→prompt bridge produces **zero marked lines today** — my fix is correct and
   activates automatically the moment a POINTER row targets an OUTWARD action, but
   it does not, by itself, reproduce a marked GitHub line in PM's next live check.

4. **Where PM's actual "file new ones, comment, close, update" text likely came
   from**: `conversational_floor.py`'s `capability_manifest_block()` (~line 479-513)
   — a raw CSV of **all 137** wired action names (`wired_chat_actions()`), injected
   into the SYSTEM PROMPT on every non-denial floor turn (line ~847,
   `manifest = f"\n\n{capability_manifest_block()}"`), explicitly labeled *"internal
   machinery: never recite these names to the user or volunteer the list
   unprompted."* It carries **zero outward/effect information** and nothing stops
   the model from paraphrasing/summarizing action names from it ("file new ones,
   comment, close, update" reads exactly like a paraphrase of
   `create_issue/comment_issue/close_issue/update_issue`). This is a plumbing gap
   too, but a **much bigger one**: fixing it would mean either decorating 137 raw
   action names with per-action outward info (defeating the block's deliberate
   "CAPABILITY-NAME-FREE" static-prose design, meant to avoid a hand-maintained
   list) or adding a parallel structured block — out of scope for this pass. Flagged
   as discovered work below, not touched.

**Gap class**: (a) plumbing, in two places — one fixed this session (the #1428→
DISCOVERY-prompt bridge), one identified but NOT fixed (the `capability_manifest_block`
system-prompt CSV, the more likely actual source of PM's observed symptom).

1. **#1428 `CHAT_POINTERS` ledger has zero POINTER rows for the comment/create-issue
   OUTWARD family** (`comment_issue`, `add_comment`, `comment_issue_query`,
   `create_issue`, `create_github_issue`, `create_item`, `create_ticket`,
   `make_github_issue`, `new_github_issue`). This is NOT a #1433 reachability-ratchet
   violation (`_derived_surfaces()` in `tests/test_architecture_enforcement.py` is

   pre-existing denominator gap rather than a build regression. But it means the
   structured "what can you do?" answer never mentions filing/commenting on issues
   at all today, marked or not.

2. **`capability_manifest_block()` (`conversational_floor.py` ~479-513) is the more
   likely actual source of PM's live "GitHub — file new ones, comment, close,
   update" text.** It's a raw comma-joined list of all 137 `wired_chat_actions()`
   names injected into the system prompt every non-denial turn, explicitly
   documented as "internal machinery: never recite these names to the user" but
   with no constraint against paraphrasing them, and carries zero outward/effect
   info. Giving this surface outwardness legibility would need either per-action
   annotations (conflicts with its deliberate capability-name-free design, meant to
   prevent a hand-maintained/drifting list) or a second structured block — a real
   design decision, not a small hunk, and outside this dispatch's scope.
