**Issue**: #1697 — files.html renders blank 'Uploaded by:' — /api/v1/files/list response has no owner_id field

## Task

`/files` renders "Uploaded by: " with nothing after it because `templates/files.html` reads
`file.owner_id` and `GET /api/v1/files/list` entries carry no owner field. Investigate the route's
actual scoping (per #1532-family principal scoping) and decide honestly: if the list is already
scoped to the current user, drop the "Uploaded by" label (noise); if shared/visible-to-others files
exist on that surface, add an `owner` display-name field and render it. No dangling label either way.

## Investigation

Read `web/api/routes/files.py::list_files` (GET /api/v1/files/list): the file-kind
query is `WHERE UploadedFileDB.owner_id == current_user.sub` — strictly
owner-scoped, no admin/cross-owner bypass for the LIST route (unlike
get_file/download_file/preview_file, which do support an admin bypass). Every
`kind: "file"` row returned IS the caller's own. The response dict for
`kind: "file"` entries omitted `owner_id` entirely; the `kind: "artifact"`
entries (same endpoint) already carry it — added in 82d8b56 (#1165 slice 3)
specifically "because files.html isOwner/delete permission needs it."

`templates/files.html`: `isOwner(file)` is `file.owner_id === window.currentUser.user_id`
and gates the delete button, the tag-edit button, and the "Uploaded by:"
indicator (`!isOwner(file)`). With owner_id missing on file-kind entries,
isOwner() silently read false for every uploaded file — not just the
reported blank "Uploaded by:" label, but (for non-admin callers) hiding the
delete (🗑️) and edit-tags (🏷️) buttons on their OWN uploaded files too.

Decision: since the LIST query is provably owner-scoped (verified by reading
the route, not assumed), the "Uploaded by" label is indeed noise for this
surface — but the root cause is that `owner_id` is load-bearing for
isOwner()-gated actions elsewhere on the same card, not just for display.
Added `owner_id` to file-kind entries (mirroring the artifact-kind
precedent exactly) rather than deleting the label from the template — this
fixes the permission-gating bug too, and (because the query is owner-scoped)
has the side effect of making isOwner() always true for a returned row, so
the "Uploaded by" branch naturally never fires. Additionally hardened
`templates/files.html`'s ownerIndicator condition to also require
`file.owner_id` truthy (not just `!isOwner(file)`), as defense-in-depth so a
future gap in the API contract can never reproduce a dangling label — this
is a template-layer guarantee, not just a today-true fact about backend data.
