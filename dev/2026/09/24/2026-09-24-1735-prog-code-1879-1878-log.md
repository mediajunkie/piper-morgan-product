**Key finding (changes severity, not the fix)**: `web/api/routes/ui.py`'s `home()` route (the ONLY place that renders `home.html`) has set `hide_floating_widget: True` since #1266 ("home renders the INLINE chat -> suppress the shell floating widget"). I rendered `home.html` via a real Jinja `Environment` both with and without that flag: **with the flag (the actual production context), there are ZERO duplicate ids today** — the widget isn't in the DOM at all on home. Without it (defensive/worst-case), duplicates existed pre-fix exactly as the issue describes. So #1879 was a **latent** landmine contingent on that render flag staying set, not a live production collision — worth flagging to Lead since it changes how urgent this was, though the fix is good hygiene either way and the id-uniqueness property is real (HTML validity, `getElementById`/CSS `#id`/ARIA-ref brittleness) independent of whether the collision is currently visible.

**Fix — renamed the INLINE component's ids** (kept the widget's `chatForm`/`chat-window`/`chat-container` unchanged): `chat-inline.html` → `chatForm-inline` / `chat-window-inline` / `chat-container-inline`. Chose this direction over the reverse because home.html's three `getElementById('chat-window')` calls are unambiguously ABOUT the inline chat (home is the page that owns it) and the widget's own class-scoped CSS was already written assuming its bare id stayed put; renaming the widget instead would have silently changed the widget's rendered dimensions everywhere (a CSS specificity fight I traced: the widget's `.chat-widget-container .chat-window` class rule currently LOSES to the bare `#chat-window` id rule on specificity, so dropping the widget's id would flip which rule wins — an unreviewed visual change I didn't want to sneak in).
- `home.html`: updated all 3 `getElementById('chat-window')` → `getElementById('chat-window-inline')`, explicit per the issue's "target the inline instance explicitly" ask.
- `chat.js`: **scoped off ids entirely** — `document.getElementById("chat-window")`/`document.getElementById("chatForm")` → `document.querySelector(".chat-window")`/`document.querySelector(".chat-form")` (both components already carry those shared classes unchanged). This was necessary, not optional: with ids renamed, chat.js's old hardcoded-id lookups would have found NOTHING on the home page (inline's ids no longer match "chatForm"/"chat-window", and the widget isn't rendered there) — i.e. home's chat would have been left with no submit handler at all. Class-based lookup binds correctly to whichever ONE instance is actually on a given page.
- `chat.css` (disclosed, out-of-owned-scope but necessary): updated `.chat-inline-container #chat-window` → `.chat-inline-container #chat-window-inline` so the full-height flex override (the #1142/#1047 fix) still beats the bare `#chat-window` rule for the inline instance.
