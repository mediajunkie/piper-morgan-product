## The fix

`_apply_subsumption_filter`'s #1738 defect-2 block. Old condition: drop the
`get_project_status` sibling iff `raw_message` matches the LIST-only
`PORTFOLIO_LIST_PATTERN` literal. New condition: drop it iff (a) a
PORTFOLIO intent survived the turn (any verb — `manage_portfolio` via
`PORTFOLIO_PATTERNS`, or `manage_repos` via `REPO_MANAGEMENT_PATTERNS`,
e.g. the "link" verb) **and** (b) every `STATUS_PATTERNS` entry that
actually matched the raw message is inside a small local set
(`status_project_noun_overlap`) copied **by value** from `STATUS_PATTERNS`
— the 9 entries that are triggered purely by project/portfolio nouns
(`\bmy portfolio\b`, `\bmy projects\b`, `\bcurrent projects\b`,
`\bactive projects\b`, `\bproject overview\b`, `\bproject landscape\b`,
`\bshow.*projects\b`, `\blist.*projects\b`, `\bprojects.*working on\b`),
as opposed to genuine status-asking vocabulary (`\bstatus update\b`,
`\bproject status\b`, `\bmy status\b`, `\bwork status\b`, `\bstatus
report\b`, standup*, progress*, "what am I working on", ...).

**What it deliberately does NOT subsume**: a STATUS match that also hits a
genuine status-asking pattern. Verified via probe — "archive project X and
what's my project status?" matches STATUS **only** via
`\bproject status\b` (not in the overlap set), so both intents survive,
unchanged. Also verified as an *improvement* over #1738's blunt
literal-anywhere-in-string check: "list my archived projects and what's my
project status" was **wrongly** subsumed at HEAD (the old rule only
checked whether `PORTFOLIO_LIST_PATTERN` matched anywhere in the raw
string, not why STATUS also matched) — under the new rule it correctly
stays two-topic, because `\bproject status\b` is a genuine, distinct ask.
Pinned as `test_two_topic_list_plus_genuine_status_phrase_now_kept`.

Not a new extraction pattern: `status_project_noun_overlap` is a local
variable inside the method (never touches `PreClassifier`'s class body, so
`TestExtractionPatternRatchet._pre_classifier_count` — which only scans
class-body `Assign`s ending in `PATTERNS` — can't see it even in
principle), and every literal in it is a value-copy of an existing
`STATUS_PATTERNS` entry, not new vocabulary. Confirmed by two guard tests
in the new file (`TestOverlapSetIsValueCopyNotNewVocabulary`) and by
`test_extraction_ratchet_stays_tight` passing unchanged.
