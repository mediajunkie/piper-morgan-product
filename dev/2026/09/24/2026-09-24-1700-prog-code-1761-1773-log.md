## #1761 — consumer_core.py fabricated-absence on MCP resource listings

**Diagnosis**: `services/mcp/consumer/consumer_core.py:_execute_list_issues` (the resources-fallback
leg of `MCPConsumerCore.execute("list_issues", ...)`) built its display dict with two prose-placeholder
`.get()` defaults:
- `resource.get("description", "No description available")` — the named site.
- `resource.get("mime_type", "text/plain")` — same class, found in the same-file sweep: asserts a
  specific, possibly-false attribute value when the field simply wasn't in the payload.

Both fabricate a definite claim indistinguishable from the server having said so — same family as
#1736 (precedent `24cd313eb`).

**Considered and NOT changed** (documented in-code, not the same class):
- `resource.get("name", f"Issue {i + 1}")` — synthesizes a positional display label consistent with
  the surrounding schema (the `number` field is the same `i + 1`), not a claim about source-provided
  content. Different class from the two fixed above.
- `resource.get("uri", "")` — empty-string default, not prose.

**Key finding driving the fix shape**: `MCPConsumerCore` is not constructed on any live production
path today — pinned by `tests/unit/services/mcp/consumer/test_no_eager_sim_stack_1699.py`
(`_count_constructions(...) == 0` for both the calendar adapter and router init paths). Grepped
`services/intent_service/`, `services/intent/`, and `web/` for any consumer of this dict shape
(`description`, `mime_type`, `list_resources`, `MCPConsumerCore(`) — zero call sites. The live
`list_issues_query` composer (`services/intent/intent_service.py:_handle_list_issues_query`) goes
through `GitHubMCPSpatialAdapter`/`GitHubIntegrationRouter`, never through this class.

**Fix** (data layer only, honest per §3): `description` and `mime_type` now read `resource.get(key)` —
`None` when absent, verbatim (including an explicit empty string) when present. No fabricated render
wording was added anywhere, because there is no live render call site to attach it to — inventing one
would have been confabulated scope. Documented this explicitly in a code comment at the fix site and
in the new test file's docstring, so whoever eventually wires this listing to a real UI knows the
honest-wording obligation (GatherOutcome §3: absent → distinct "no description provided"-style
wording, never silently treated as empty) still needs to land at that future render site.
