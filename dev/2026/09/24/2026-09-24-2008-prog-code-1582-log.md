  `web/static/js/loading.js` (`_escapeHtml` class method — underscore
  prefix, ES6 method shorthand, no `function` keyword) and the
  `_escapeHtml`/`_escapeAttr` pair pinned by
  `tests/unit/templates/test_suggestions_xss_escaping_1741.py` (chat
  suggestion-card renderer's own namespaced helper).

This means 8 templates currently ship the vulnerable quote-incomplete variant
in production — consolidating onto the shared quote-complete implementation
FIXES those 8 attribute-injection holes as a byproduct of the ratchet, not
just prevents a hypothetical future one. Filing this as discovered work (see
below) since it's a bigger finding than the issue's stated scope.

Load order: all 9 top-level templates in scope `{% extends
"layouts/app_shell.html" %}` and put their inline `<script>` in
`{% block scripts %}` (after app_shell's own shell-owned script tags). Added
`escape.js` to app_shell.html alongside `mobile-nav.js` so every extending
page gets it for free, before `{% block scripts %}`. The two `components/`
partials (`greeting_context.html`, `project_config_panel.html`) are
`{% include %}`'d inside pages that extend app_shell (project_config_panel via
project_detail.html; greeting_context currently has ZERO include sites
anywhere — orphaned/unwired, confirmed via grep — noted, not fixed, out of
scope). All actual escapeHtml/escapeAttr call sites in these templates run
from event handlers (DOMContentLoaded, fetch callbacks, onclick) fired after
full synchronous script parse completes, so document-order placement of
escape.js relative to these inline scripts doesn't affect correctness as long
as it's a plain synchronous `<script src>` (confirmed: no top-level
immediate calls found).
