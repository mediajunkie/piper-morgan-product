## What I found

- `services/integrations/slack/response_handler.py` (`_fetch_sender_llm_key`) fetched
  ONLY the sender's stored `anthropic` key and bound it via the `str` form of
  `request_api_key` (normalizes to `{"anthropic": key}`). A sender with no anthropic
  key stored — including an openai-only sender — got nothing bound, so any LLM touch
  raised `UnboundLLMKeyError` and the handler answered the honest-but-narrow "no key of
  your own" refusal, even when they held a perfectly good OpenAI key.
- The shared resolver the web routes use: `web/utils/llm_key.py::expand_llm_key_binding`
  (#1819) — widens an already-resolved anthropic key into `{"anthropic": ..., "openai":
  ...}` via the module's `_fetch_stored_provider_key(user_id, provider)` fetcher. Used by
  `web/api/routes/intent.py:596` and `web/api/routes/documents.py:81`.
- **Gotcha that shaped the design**: `expand_llm_key_binding(None, user_id)` returns
  `None` *unchanged* — because its contract assumes `resolved` came from
  `resolve_request_api_key`, whose only legitimate `None` is the #1807 designated-OPERATOR
  seam. Slack never calls that resolver (it fetches the anthropic key directly), so a
  Slack sender's "I simply have no anthropic key" is NOT the same value as "the operator
  authorized the server's key" — calling `expand_llm_key_binding` directly with a
  possibly-`None` anthropic fetch would have silently smuggled the operator's key to a
  keyless linked sender. That would have been a REAL security regression, so I could not
  reuse the entry point verbatim; I reuse its two building blocks instead (see below).
- Provider SELECTION (which of a both-keys binding actually gets spent) is fully separate
  from key binding: `services/llm/provider_selection.py` (per-user default -> server
  default -> env -> first available) plus `LLMClient._complete_raw`'s primary-then-
  fallback loop in `services/llm/clients.py` (~L357-506), keyed by `user_id`. Slack already
  passes `piper_user_id` into `intent_service.process_intent(user_id=...)`, so once the
  binding is widened, selection is 100% inherited from the same shared code the web
  routes use — Slack invents no precedence of its own.

## The fix

`services/integrations/slack/response_handler.py`:
- New method `_fetch_sender_llm_key_binding(piper_user_id) -> Optional[Dict[str,str]]`:
  - sender HAS a stored anthropic key -> calls `expand_llm_key_binding(anthropic_key,
    piper_user_id)` — the literal same call the web routes make (#1819).
  - sender has NO anthropic key -> fetches their stored openai key directly via
    `web.utils.llm_key._fetch_stored_provider_key(piper_user_id, "openai")` (the same
    per-provider fetcher `expand_llm_key_binding` uses internally) and returns
    `{"openai": key}` if present, else `None`.
  - No `piper_user_id` -> `None` immediately, no DB touch (unchanged #1809 contract).
  - Any fetch exception -> logged, fail-closed to `None` (unchanged fail-closed contract).
- `handle_spatial_event` now calls this instead of the old anthropic-only
  `_fetch_sender_llm_key`, and binds the resulting dict via `request_api_key(...)` when
  truthy. `_fetch_sender_llm_key` itself is UNCHANGED (kept as the anthropic-only leg,
  now only called from inside the new method) — no other call site touched it.
- Comments in `handle_spatial_event` updated to describe the provider-keyed widening and
  explicitly flag the `expand_llm_key_binding(None, ...)` == operator-seam gotcha so a
  future reader doesn't reintroduce it.
