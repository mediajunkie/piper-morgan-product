## Task

#1792: `TokenBlacklist.is_blacklisted` fails closed by returning `True` on any exception.
`JWTService.validate_token` reads that as "revoked" and raises `TokenRevoked`; every
handler turns that into **401 "Token has been revoked"**. A Redis blip therefore tells
every active user a specific, alarming, FALSE thing about their own security state.

Fix: keep failing closed, but report the honest 503 "couldn't verify right now" shape,
matching the in-repo precedent `require_admin` already set.

### Fix

New `BlacklistUnavailable` in `services/auth/jwt_service.py`, raised by both store
sites, re-raised explicitly in `validate_token` (the generic `except Exception` there
would otherwise have rewritten it to `TokenInvalid` — a different false claim), and
handled at every refusal surface:

| Surface | Before | After |
|---|---|---|
| `auth_middleware.py` `dispatch` | 401 "Token has been revoked" | 503 via new `_service_unavailable_response` |
| `auth_middleware.py` `get_current_user` | 401 `TOKEN_REVOKED` | 503 `REVOCATION_CHECK_UNAVAILABLE` |
| `web/api/routes/standup.py` | 401 `TOKEN_REVOKED` | 503 `REVOCATION_CHECK_UNAVAILABLE` |
| `web/api/routes/auth.py` refresh | 401 + **cookie clear** | 503, cookies untouched |
| `MCPAuthAdapter.validate_mcp_token` | `None` ("invalid") | propagates (deliberate) |

The 503 response deliberately does **not** redirect browsers to `/login` the way
`_unauthorized_response` does — that is the same false story in a different costume,
and login doesn't consult the blacklist so the user would loop.

**Tension, stated rather than resolved silently: there isn't one.** `return True` meant
"refuse" and `raise` also means "refuse". Nothing is granted on error before or after.
Only the claim attached to the refusal changed. The red-first run proves this
independently: the two "still refuses" tests and both "genuinely revoked" tests passed
*before* the fix — only the three honest-message tests were red.

### Discovered work — #1802 filed

"A bare TestClient gets one authenticated request" is a **separate** defect, not a
symptom of this one: after the fix the sequence is `200, 503, 503, 503, 503` — honest
now, still broken. Root cause is two layers below #1792: (1) bare `TestClient` skips
startup so `TokenBlacklist.initialize()` never runs and `_redis_available` stays False
*silently*; (2) `_check_database` uses the unguarded `AsyncSessionFactory.session_scope()`,
whose pooled asyncpg connection belongs to a dead loop by request 2.

**This also discharges #1792 AC item 5** (does a same-loop reuse guard belong in the
Redis factory?): **it belongs there and it is already there** — `RedisFactory.initialize`
rebuilds the pool on loop change, added by #1452 for this exact failure class. The gap
is on the **database** side, where `session_scope_fresh()` (#442) is a manual opt-in
nobody told `_check_database` about.
