## What I found

### The bug (confirmed via `gh issue view 1810` / `gh api`)

`web/api/routes/setup.py` `complete_setup()` (~:1021-1041, citing #724) stored
each user's OpenAI/Anthropic key **twice**:
- `{user_id}_openai_api_key` / `{user_id}_anthropic_api_key` — correct, per-user
  (via `UserAPIKeyService.store_user_key(..., username=user_id)`,
  `services/security/user_api_key_service.py:198`).
- `openai_api_key` / `anthropic_api_key` — a GLOBAL, unprefixed copy
  (`keychain.store_api_key("openai", req.openai_key)` — no `username=`),
  justified in a comment as "so LLMClient can find keys during server
  startup when no user context exists."

That global slot is exactly what `LLMConfigService.get_api_key(provider)`
(`services/config/llm_config_service.py:213`) resolves — keychain-first,
env-fallback, with **no per-user parameter at all**. Every user who
completed setup silently overwrote whichever key the operator or an
earlier user had in place. Last-writer-wins, no audit, no confirmation —
exactly as #1810 describes.

### PM ruling that unblocks the fix (decisions.log, 2026-09-14 17:30 PT)

"THE SERVER KEY IS NOT A REAL CONCEPT AND WILL NOT BE SUPPORTED IN ANY
SENSE." Evidence in #1812: background/scheduled jobs make zero LLM calls;
startup only wires an `OutputFilter` and never completes a request;
setup-time validation tests the key being submitted. #724's stated
startup-consumer justification does not survive tracing.

## Test — red-first, real abstraction, no mocks of KeychainService

New file: `tests/unit/web/api/routes/test_setup_global_key_write_1810.py`
(2 tests, `TestNoGlobalKeyWriteOnSetupComplete`):

- `test_complete_setup_writes_per_user_key_never_global`
- `test_second_user_completion_cannot_clobber_first_users_key` (drives the
  exact "last-writer-wins" scenario #1810 names, with two real users)

Both drive the **real route function** (`complete_setup`, not a mock of a
helper) against the **real `KeychainService`** abstraction — no mocking of
`get_api_key`/`store_api_key`/`delete_api_key` themselves. To keep this
deterministic and dialog-free on a Mac dev box (real OS keychain would pop
a permission prompt), an autouse fixture forces `PIPER_CREDENTIAL_STORE=db`
+ a valid `ENCRYPTION_MASTER_KEY` for the test's duration, routing
`KeychainService` onto the real `EncryptedDBCredentialStore` (#1382) against
the real local Postgres (5433) — same class of substitution
`tests/security/test_secure_credential_store_1382.py` already uses. The
fixture snapshots the two global provider slots before the test and
restores/deletes based on that snapshot afterward (never blind-deletes —
this Postgres is a real, potentially-shared dev DB; CLAUDE.md's "pause
before irreversible actions").

Real users are created via the `db_session` fixture (needed: `UserAPIKey`
has an FK to `users.id`) and cleaned up explicitly in a `finally` (this
DB is not a transactional-rollback fixture). Keys use `secrets.token_urlsafe`
in the exact provider format (`sk-...` / `sk-ant-...`, correct length) so
the real format/strength/leak validator in
`services/security/api_key_validator.py` passes without being mocked.
