## The fix — layer and rationale

**Layer chosen: credential resolution in `LLMConfigService.get_api_key`, reading the EXISTING
per-request ContextVar.** Not a second resolution mechanism: no `UserAPIKeyService` import, no
`user_id` plumbing, no DB access added to a sync, DB-free service. `get_api_key` now reads the same
ContextVar that `anthropic_client_for_request` reads, so the gate and the consumer are physically
incapable of disagreeing — which is what the bug actually was.

Considered and rejected: teaching `LLMConfigService` to query `UserAPIKeyService` by `user_id`.
That is a second credential path (async + DB in a sync service), and it would have re-fetched a key
the request had already resolved 4 frames up. The "one path, not two" lesson from the
acceptance-contract and server-key work applies directly.

Three files:
1. `services/llm/request_key.py` — new `REQUEST_KEY_PROVIDER = "anthropic"` constant. The
   ContextVar's key IS an Anthropic key by construction (`web/utils/llm_key.py` fetches provider
   `"anthropic"`; the header is documented as an Anthropic key; `anthropic_client_for_request` is
   its only consumer). Naming it once beats each new reader re-hardcoding `"anthropic"`.
2. `services/config/llm_config_service.py` — `get_api_key(provider, *, include_request_key=True)`
   gains a Priority 0 that returns the request-bound key for `REQUEST_KEY_PROVIDER`.
3. `services/llm/clients.py` — `_init_clients` now passes `include_request_key=False` and gates each
   client on a truthy SERVER key.

⚠️ **(3) is not cosmetic — without it the fix introduces a cross-user credential leak.**
`LLMClient()` is constructed lazily INSIDE a request in three places (`intent_service.py:5248` and
`:6772`, `conversational_floor.py:1633`, `semantic_boundary_detector.py:524`). A request-aware
`get_api_key` in `_init_clients` would bake one user's BYOC key into a long-lived singleton and
spend it for the NEXT caller. Pinned by
`test_server_singleton_client_never_captures_a_request_scoped_key`.

**Why a keyword flag rather than a second `get_server_api_key` method**: `scripts/check_unscoped_reads.py`
(ADR-079 D2a) counts `*.get_api_key(provider)` with no principal. Renaming the three `_init_clients`
call sites out of that method name would have silently dropped 3 real hits from a *security*
ratchet — coverage loss disguised as a ratchet improvement. The kwarg form keeps them counted
(unscoped_reads stays at its 52 ceiling, measured).

**No server-owned key reintroduced.** Step 0 surfaces only a key the caller already supplied.
Keyless callers bind nothing, and `_init_clients` is explicitly request-blind.
