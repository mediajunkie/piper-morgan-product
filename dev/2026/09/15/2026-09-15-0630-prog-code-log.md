## Discovered work

**Filed [#1814](https://github.com/mediajunkie/piper-morgan-product/issues/1814)** (bug): post-#1810,
`LLMConfigService.get_configured_providers`/`get_api_key` never consults a user's own stored key —
only the legacy global/bare keychain slot, which #1810 correctly stopped populating this week. Result:
any signed-in user whose only key is their own (the #1807-sanctioned, now-only-supported state) gets
"no LLM provider configured" on every floor-routed query (DISCOVERY, IDENTITY, GUIDANCE non-setup,
CONVERSATION non-greeting, TEMPORAL, STATUS, PRIORITY, UNKNOWN) — most of what a real user asks after
the first greeting — even though the correctly-wired per-request BYOC code
(`anthropic_client_for_request`, #1162/#1807) is sitting right there, just unreachable because the
upstream "is anything configured" gate never looks at the per-user key. This is the live, present-tense
gap Janne will hit on his very first non-greeting question, immediately after doing exactly what the
invite instructs (configuring his own key). Distinct from #1809 (which is about *unbound* calls
silently spending the server key when one exists) and from #1812 (the philosophical "should a server
key exist at all" question) — this is neither of those: no server key AND the per-user key isn't
checked either, so a perfectly valid personal key still produces a false "not configured" message.
Traced to root cause (not guessed), full evidence and file/line citations in the issue body.
