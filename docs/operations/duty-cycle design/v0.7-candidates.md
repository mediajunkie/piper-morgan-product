## Candidate 1: Commit-cadence-during-no-op-fires

**Surface date**: 2026-05-26 (CIO Phase B Day-2)
**Surfaced by**: CIO (own observation, filed in attention doc); confirmed by Docs Day-1 (2026-05-27) at second instance
**Severity**: moderate (operational; cohort-CI-volume contributor)

**The pattern**: each cron fire commits + pushes a cycle log entry, including no-op fires. Cohort-wide: 7-11 agents × hourly × 8-10 active hours = ~80-110 commits/day of mostly-no-op data. Adds to push-triggered CI run volume (which the GitHub Actions refactor lane just surfaced as 559/307 daily runs).

**Proposed treatments**:
- (a) Batch zero-work cycle log entries; commit at next substantive fire OR at STOP
- (b) Commit zero-work entries but suppress push (commit locally; push at next substantive)
- (c) Skip cycle log appendage entirely on zero-work; track only in session log

**Lean**: (a) preserves audit + reduces noise. Convergent with GitHub Actions paths-filter refactor lane (Lead Dev driving).

## Candidate 2: Hourly-interval-delay during burst-days

**Surface date**: 2026-05-27 ~10:54 AM PDT
**Surfaced by**: PM (observation during Phase D scaling)
**Severity**: low-moderate (visible structural latency during high-traffic windows)

**The pattern**: with hourly intervals + multiple adopters launching simultaneously, average wait for cross-role mail is ~30 min; worst case ~60 min. Burst-day mail piles up faster than fires drain it.

**Proposed treatments**:
- (a) Status quo: hourly + accept delay during burst; PM-engagement-pause handles high-priority
- (b) Temporarily tighten interval during identified high-traffic windows (e.g., */20 just for adoption-burst days)
- (c) Burst-mode pattern: auto-tighten interval when cohort cycle log writes exceed threshold

**Lean**: (a) for steady state; (b) on PM-demand during cohort-launch days; (c) too complex per "formalize-not-proliferate".

## Candidate 3: Foreign-agent-commit-recovery on shared checkout

**Surface date**: 2026-05-27 (HOST Day-1)
**Surfaced by**: HOST observation (Fire 2 — Docs commit `27aaf5520` appeared during sync; pull --rebase --autostash recovery); CIO observed multiple instances throughout the day
**Severity**: moderate (Pattern-067-family novel failure mode; frequency scales with cohort size)

**The pattern**: cycle agents sharing single main checkout can pick up each other's unpushed commits during pull operations. Pull --ff-only fails when divergent; --rebase --autostash works.

**Proposed treatments**:
- (a) Document the recovery pattern as a procedure (immediate fix)
- (b) Structural: worktree-default for substantive cycle work (each agent on own branch; eliminates the clash class)

**Lean**: (a) for immediate; (b) as deeper structural fix. Convergent with existing CLAUDE.md worktree-default guidance for substantive sessions.

## Candidate 4: Per-role interval defaults based on traffic density

**Surface date**: 2026-05-27 (HOST + Docs Day-1; Exec separately)
**Surfaced by**: HOST Day-1 (all 4 fires sub-2-min triage — hourly may be over-calibrated); Docs Day-1 (3 consecutive zero-mail hours — hourly over-frequent during quiet windows); Exec interval-clarification question
**Severity**: moderate (real per-role variance; affects commit volume + responsiveness trade-off)

**The pattern**: v0.6 design doc says "10-30 min during active hours"; my Phase D rollout memos said "hourly recommended" for cohort scaling. Real traffic density varies by role; hourly is over-calibrated for thin-traffic roles (HOST, Docs in afternoon) and potentially under-calibrated for coordination-heavy roles (Exec).

**Proposed treatments**:
- (a) Rewrite v0.6 design §"Cron interval guidance" to distinguish design-validation phase (dense fires) from cohort steady-state (interval for utility-vs-load balance)
- (b) Per-role default recommendations (workhorse-tier hourly; thin-traffic 2-hourly; coordination-heavy 30-min)
- (c) Adaptive interval based on observed traffic density (probably over-engineered)

**Lean**: (a) + (b) combined; (c) deferred.

## Candidate 5: PM-absence-detection automated threshold

**Surface date**: 2026-05-27 (Lead Dev pro-tips ask + PM-implied)
**Surfaced by**: Lead Dev (asking how cohort auto-resumes); PM (observation that "some agents are able to go to IDLE after I am absent for a while")
**Severity**: moderate (currently heuristic; PM wants formal mechanism)

**The pattern**: Rule 2 PM-presence-pause + go-autonomous signal. CIO uses heuristic (closure-marker-reading + ~5-10 min silence proxy). Lead Dev had ~45 min PM-silence Day-1; heuristic worked. No observed over-eager-resume failures because default is wait.

**Proposed treatments**:
- (a) Status quo: heuristic-based wait-default; document the heuristic but no automation
- (b) Formal mechanism: after PM-presence-pause, start timer; if no PM message for silence_threshold (e.g., 15 min) AND no "stay-paused" marker → auto-resume cron
- (c) Tone-reading remains discipline-side; threshold becomes mechanism-side

**Lean**: (b) is genuinely the right work item; bounded scope; aligns with PM's stated direction.

### 2026-06-02 investigation update (PM-requested "which agent's early cycle was best at IDLE")

A cohort-wide review of early cycle logs (May 25–27) confirms and sharpens this candidate:

- **Best at BOTH IDLE-detection and interruption-persistence: CIO's own pilot cycle.** Mechanism = a **wait-default re-arm heuristic**: never re-fire until a positive PM-absence signal appears — *closure-marker-reading + tone + ~5–10 min silence proxy* (`dev/active/cycle-log-cio-2026-05-27.md:258`). PM noticed at the time and pointed Lead Dev to CIO for tips (`:254`). CIO also had the only verified **overnight clean re-arm** (conditional-dispatch; `canonical-cron-prompt-template-v0.7.md:102`).
- **Architect**: cleanest *mechanical* pause (CronDelete-FIRST, Rule 1) but never PM-interruption-tested. **Lead Dev**: the negative example — missed the pause AND never re-armed (dead overnight cron; `cycle-log-lead-2026-05-27.md:7,79`).
- **Myth-correction**: the cohort did NOT write divergent bespoke cron *prompts* — every adopter copied CIO's verbatim template. So the quality spectrum PM remembers is **behavioral execution of the rules**, not prompt-text. The good prompt was always CIO's.
- **The regression mechanism (key)**: normalization onto the lighter canonical template (~30 lines) replaced CIO's *graded* wait-default heuristic with a *binary* "PM-message → CronDelete / go-auto → CronCreate." The graded heuristic — the thing that made CIO's cycle stay-IDLE-through-interruption — was dropped in the normalization. **That is why IDLE-resume feels lost.**
- **Fix is therefore restoration, not invention**: re-add CIO's wait-default heuristic (closure-marker + tone + silence-proxy) to the canonical cron prompt + this candidate's treatment (b). The silence-fallback PoC = formalizing our own proven approach.

**Delivery mechanics confirmed** (resolves the open "how does a fire reach a continuing session" question — same as Janus Q2): the fire is a **prompt injected into the running REPL session** (no file/queue polling; `duty-cycle-design-v0.6.md:57`). Cron is **session-scoped — if the session isn't running when it fires, nothing happens** (`cycle-log-cio-2026-05-25.md:219`); overnight autonomy requires the session to stay alive. Runtime **idle-suppression** fires "when the REPL is idle," which makes Rule 2 relaxable (PM messages are spaced) but does NOT cover the inter-tool-call gap during multi-step work — which is why Rule 1 stays strict (`procedures/cron-lifecycle.md:58,61`).

## Candidate 10: Worktree-as-cycle-default (reverse v0.6 architectural decision 3) — TOP v0.7 ITEM

**Surface date**: 2026-05-28
**Surfaced by**: Docs shared-main-clash root-cause memo + PM worktree-as-rule instinct (~06:55-07:05 PDT) + Arch's cron already running in a worktree (proof-of-concept)
**Severity**: HIGH (architectural; the most significant v0.7 item)

**The pattern**: v0.6 decision 3 ("cycle runs on main, no per-day branch") was made when the cycle was CIO-only (May 24). At cohort scale (8-11 concurrent autonomous agents), shared-main becomes a clash engine: Docs documented 29 commits to main in 8 hours from multiple agents + external Janus push, all same git identity, each fire doing `pull --rebase --autostash` → merge commits, leftover stashes, non-ff scrambles. Two failure modes: (1) uncommitted-edits-across-rebase (discipline-fixable); (2) concurrent-commit-rebase-churn (architectural, NOT discipline-fixable).

**Proof-of-concept**: Arch's cron already runs in a worktree (`cd <worktree>`); Arch's overnight fires didn't generate the clash cruft.

**Proposed treatment**:
- Reverse v0.6 decision 3: each agent's cycle runs in dedicated `claude/{role}-cycle` worktree
- Substantive work commits to worktree branch; merges to main at natural points (STOP or per-task)
- Mailbox writes stay on main (existing discipline) via brief checkout-commit-return, batched
- Merge-keeper sweep catches stranded work
- Aligns cycle with existing worktree-default discipline that decision 3 had opted out of

**Ownership**: PM ratification + Lead Dev/Architect implementation design. CIO cycle-design recommendation: REVERSE decision 3.

**Status**: filed as cohort synthesis memo 2026-05-28 (CIO → Lead+Docs+Arch+HOST CC PM); awaiting ratification.

## Candidate 11: Autonomy relocates the bottleneck to the convergence point (PA + PM, 2026-06-03)

**Surfaced by**: PM's framing + PA's attention-dashboard v0.1 (`pa-cohort-attention-rollup-2026-06-03.html`).
**Severity**: strategic — the success-mode failure of the duty cycle.

**The claim**: the duty cycle moves work off the PM-blocking path; when it works, the bottleneck doesn't vanish — it **relocates to the one thing that can't be parallelized: PM's attention.** Ten self-draining agents each correctly surfacing only their few real PM-decisions still sum to a fragmented decision surface no single doc shows. So the **attention dashboard** (PA's rollup of all `duty-cycle-escalations-*.md`) is not a reporting widget — it's the *counterpart mechanism* to autonomy succeeding, and the PM-welfare guard. Pairs with the derived cohort-status view (`scripts/cohort-cycle-status.sh`) as the two halves of derived duty-cycle observability (both methodology-36). **Promote to**: likely a standalone methodology entry ("Autonomy Relocates the Bottleneck to the Convergence Point") + the dashboard as a named roadmap item. CIO to draft.

## Candidate 12: Conceptual-model carriers vs execution-mechanics (Comms, 2026-06-03)

**Surfaced by**: Comms Finding 3 (Day-1 cycle findings); converges with CIO 360 §5.5 (corpus holds entries, not the retrieval/model layer).
**Severity**: methodology-shape.

**The claim**: loaded surfaces (templates, voice guides, skills) capture *execution mechanics* but not the *conceptual model* of a practice, so each fresh session reconstructs the stance from mechanics and gets it wrong (Comms: the narrative practice re-explained nearly every session despite ~a year running). **Fix shape**: canonical method-doc = the knowledge; task-scoped **skill** = the loaded carrier that embeds the model (loaded-on-invocation); hook = discoverability backstop only. **Cohort probe worth fielding** (360-adjacent): "what conceptual model does your lane rely on that isn't written down anywhere that *loads*?"
