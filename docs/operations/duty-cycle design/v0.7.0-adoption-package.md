## TL;DR — get cycling in 4 steps

1. **Create your worktree + launch your session inside it** (Model A — see below). DO NOT register on shared main.
2. Copy the cron prompt from `canonical-cron-prompt-template-v0.7.md`; fill `{ROLE}` + your STATE paths + pick an open offset minute.
3. Register the cron from inside the worktree session (when PM signals go-autonomous).
4. Each fire follows the cron prompt's procedure: CronDelete-first-if-substantive → sync → mail-check → CHECK dispatcher → work → cycle-log → commit + push branch:main → re-CronCreate at IDLE.

## The two adopter paths

**Fresh adopters (no existing cron / never launched a cycle) — Comms, Web, PPM, CXO:**
- `git worktree add -b claude/{role}-cycle ../piper-morgan-product-{role}-cycle main` (from the main repo dir)
- **Open Claude Code IN `../piper-morgan-product-{role}-cycle`** — this is Model A from the start, no migration.

**Migrate-from-Model-B-or-on-main (already cycling but launched-in-main) — CIO:**
- Same worktree create, then **relaunch the session inside the worktree** (an operator action — a cron can't self-relaunch). Until you relaunch, you're Model B: cwd resets between Bash calls, so chain every git op in one `cd <worktree> && …` command.

**Why launch-IN-worktree is load-bearing**: cwd anchors to wherever the *session* was launched, not to the cron prompt's `cd`. Launch in the worktree → cwd stays there → no per-command cd, and merge is a clean `git push origin claude/{role}-cycle:main` that never touches main's working tree.

## Cron-script comparison + best-practices (the normalization)

The cohort's improvised cron scripts spanned a spectrum: **Lead's ~6 lines** (too terse — assumes fluency new adopters lack) to **CIO/Docs's ~40 lines** (heavier than needed once fluent). The **canonical template is the normalized middle-weight (~30 lines)**: critical semantics inline, everything else by-reference to `procedures/`. Adopt the template; don't re-improvise.

**Load-bearing norms (the best-practices, all baked into the template + cron-lifecycle.md):**
- **CronDelete-FIRST** — if a fire may go substantive (>2 min), CronDelete as the literal first action (before sync). Closes the CronList→CronDelete race where a re-fire slips into your inter-tool-call idle gap (Arch Fire-3; the clash is REPL-turn-level, NOT prevented by worktree-isolation or idle-suppression). **Rule 1 stays strict; it governs over Rule 2 when work is substantive.**
- **Rule 2 = Model-A relaxation** — do NOT CronDelete for PM presence; leave the cron running during PM conversation (runtime idle-only-fire suppresses between PM's spaced messages).
- **Drain-until-IDLE** — each fire drains ALL unblocked work (mail-to-zero → tasks-to-blocked → re-check → loop), then pronounces (0,0) IDLE. Not one-work-unit-per-fire. No-op IDLE ticks need NO commit (don't churn the log).
- **Explicit-paths-only** on git add — never directory-level mailbox adds.
- **Verify-first** before authoring any new methodology/pattern entry; read the WHOLE source artifact before declaring a referent ambiguous.
- **Offset discipline** — pick a minute not already taken (slate below); spreads fleet load off the :00/:30 marks.

## Interim mechanisms (until the two refinements land)

- **Mailbox writes → main-worktree bridge**: `check-branch.sh` hard-blocks (`exit 2`) any `mailboxes/` commit on a non-main branch (PA confirmed 2026-05-28, no bypass). So mail does NOT ride the per-fire push-to-ref. Instead: cd to the main repo → pull → write → commit → push → return. Batch mail to minimize the switch. (If Lead amends the hook, this switches to the clean push-to-ref path.)
- **Overnight → manual morning restart**: when your session dies (sleep/battery), the next-day START is a manual reopen-in-worktree (PA + CIO both did this). The conditional-dispatch cron only auto-STARTs the new day if the session survived the night.
