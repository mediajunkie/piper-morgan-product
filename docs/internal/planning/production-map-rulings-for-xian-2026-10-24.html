Bottom line. The reviewers agree on almost everything. Eight calls are yours. Each one has my recommendation, so “all as recommended” is a valid answer. Once you’ve answered, PPM files and moves the issues, and I write the brief for the living map. About 15 minutes.

The eight calls

1. One production instance, plus a separate staging instance.

Alpha’s Fly app is already production, and every audience has been served from it. Arch recommends keeping one production instance, with audiences as product gates, so there’s no 1.0 instance and no migration. Add a staging instance for destructive tests and release rehearsals (Thursday’s test stopped the database the partners’ data lives in). Staging holds made-up data only and is never copied from production. It has its own keys, can’t email or message anyone, and shows a banner. Backup restore tests use a separate short-lived copy that is destroyed afterwards. Cost: one more small Fly app and database.

Recommend: yes.

2. What “1.0” means.

(a) Every Production issue closes. About 50 of them aren’t promises to users (test health, dead code, polish), so they would gate the 1.0 release. (b) Every 1.0 promise has a closed issue and main is green. The rest moves to Ongoing or to a health backlog that doesn’t gate.

Recommend: (b). It makes the map able to show “how close to 1.0”. PPM counted the 50 by title only and would read them before moving any.

3. Rewrite ESSENCE commitment 6 (“not a destination app”).

Your August surface rulings and this week’s PDR-005 and PDR-006 amendments make the web app a real surface. Sprint E (34 web issues) only makes sense if it is.

Recommend: yes. Arch drafts the new wording, and you ratify it.

4. Drafting a PRD or spec: 1.0 or after?

ESSENCE commitment 2 includes Piper drafting PRDs and specs. Nothing in Production builds it. #2139 is the nearest.

Recommend: after 1.0, noted in ESSENCE. 1.0 stays smaller, and the drafting work rides on the document and GitHub capabilities once they’re solid. If you see it as core to “a PM’s assistant”, say 1.0, and PPM files it under Doc.

5. PDR-001: the setup wizard as a recorded exception to “recognition first”.

CXO’s wording: “recognition-first applies to the first conversation; the hosted setup wizard is a stepped, explicit-consent flow, and is the recorded exception.”

Recommend: adopt CXO’s wording. Whether Piper’s first conversation actually recognizes the user today is unchecked. That’s #1538’s work.

6. How public-beta users get in.

Every account today starts from an invite code minted by hand. Public beta needs either open sign-up or a waitlist, plus per-account rate and abuse limits.

Recommend: a waitlist first, with you admitting people in batches and the abuse limits built before it opens. It keeps the rule that nothing needs a second person, and it lets you pace support. Open sign-up can come later.

7. A Readiness lane, which gates public beta.

A short list of things that must exist before strangers arrive, each one backing a promise in the Terms: the restore test, account deletion, data export, support intake and an outage notice. Other backstage work goes to Ongoing, with no gate. Exec owns the lane, and HOST’s send-morning checks become its standing check. All reviewers agree.

Recommend: yes.

8. What “main green” means, and how much of each sprint goes to health work.

Main’s 12 check workflows are green today. The full test suite is not: #1452 shows hundreds of failures, and #1457 (ci.yml) has been red for 100+ runs. The honesty sprint’s ratchets need a suite that runs green.

Recommend: “green” means the 12 workflows now, and the full suite by the end of the honesty sprint. Health work takes about one issue in five of every sprint until then. This is the old “CI target” question from your list.
